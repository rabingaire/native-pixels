8.1Draw inside the frame#

The background proves that the application can acquire, clear, submit, and present an image. To draw a triangle over it, we need a shader that supplies its corners and a shader that supplies its color.

We will create shaders/character.wgsl and extend the renderer with a pipeline that selects those shaders. The first shader stores three fixed corners so we can learn shader syntax without also learning vertex-buffer layout.

8.2Read the shader language#

WGSL is the language for the small programs our GPU executes. Its spelling differs from Odin, but the same ideas apply: values, procedures, inputs, and returned results. Read these spellings before the complete shader:

WGSL spellingMeaning here
fn vs_main(...) -> vec4fA function that returns four floating-point numbers. WGSL calls a procedure a function.
f32, u32A 32-bit floating-point value, or a nonnegative 32-bit integer.
vec2f(x, y), vec4f(x, y, z, w)Two or four f32 components grouped as a vector.
array<vec2f, 3>Three two-component vectors, indexed from zero.
let positions = ...;Give a local value a name; this value cannot be reassigned.
@vertex, @fragmentMark functions that the graphics pipeline can run at those stages.
return value;Return a result. WGSL statements end with a semicolon.

The vertex shader returns a clip position (x, y, z, w). WebGPU keeps points where x and y lie between −w and +w, and z lies between 0 and w. It then divides x, y, and z by w to obtain normalized device coordinates, or NDC. We choose z = 0 and w = 1, so the division leaves x and y unchanged.

For this first triangle, x = −1 is the left edge, x = +1 the right edge, y = +1 the top, and y = −1 the bottom. The center is (0,0). These are coordinates relative to the output region, not pixel numbers. Three corners inside these bounds give us a visible triangle.

8.3Start with the smallest possible shader input#

We already have a valid render pass. It needs a pipeline and a draw. To avoid introducing buffer layout and shader syntax simultaneously, the first vertex shader keeps three positions in a constant WGSL array. The GPU supplies a built-in vertex index. Drawing three vertices invokes the shader for the three entries and assembles their outputs into one triangle.

Add shaders/character.wgsl. The name anticipates its role later; today it is a triangle shader. WGSL is compiled by the native implementation into the backend shader language or machine representation it needs. There is no separate browser runtime and no need for us to write a Metal or HLSL version.

@vertex identifies the vertex entry point. @builtin(vertex_index) requests an input generated by the draw machinery rather than loaded from our vertex buffer. The returned @builtin(position) is the clip position the rasterizer needs. Its z=0 and w=1 keep our 2D triangle inside WebGPU’s depth clip interval and make clip x/y equal NDC x/y.

@fragment marks the fragment entry point. Its @location(0) output goes to color target zero. This location is not a pixel coordinate, a bind-group binding, or a buffer slot. Shader interfaces have distinct namespaces that we will keep separate as the program grows. The constant RGBA color is linear-light green with alpha one.

8.4A module is code; a pipeline is a configured program#

Extend renderer.odin with a Renderer struct containing the pipeline handle, plus renderer_init and renderer_destroy. In main, initialize this renderer after GPU setup and register its cleanup. Pass the renderer pointer into renderer_frame. These are related changes: a persistent resource needs an owner and a way to reach its per-frame use.

In src/renderer.odin: Inside the new renderer_init procedure, place this block at the beginning of its body, before target :=. The complete file supplies the procedure signature. Complete file with surrounding code.

#load embeds the shader text at compile time relative to the Odin source file. The executable does not depend on its working directory to find a shader. Editing WGSL requires rebuilding; there is no hot reload. The ShaderSourceWGSL extension uses the same descriptor-chain mechanism we saw for native surfaces, with a discriminator telling WebGPU how to interpret its source.

A shader module can contain several entry points. Creating it parses and validates source, while pipeline creation also checks stage interfaces and target compatibility and may perform expensive backend compilation. The pipeline keeps the implementation data it needs; we can release our shader-module handle after creation. Error callbacks remain essential because an invalid shader can produce an error object even when the handle is not nil.

A pipeline layout describes resource inputs supplied to shaders. A bind group is a set of those inputs. This shader uses only its own fixed values, so its layout has zero bind groups. Creating an empty layout records that choice explicitly.

The pipeline knows the target format because output conversion and blending must be valid for that format. A floating-point shader result cannot be written under arbitrary target assumptions. This also lets the implementation compile state before the frame is recorded. It does not know this frame’s texture handle or window size. Those are render-pass and viewport concerns, which is why resizing alone will not require a new pipeline.

8.6A draw finally appears#

The draw arguments are vertex count, instance count, first vertex, and first instance. We need three vertices and one instance, starting at zero. Selecting the pipeline establishes the executable state for subsequent draw commands in this pass. It does not itself render. The draw is still only a recorded command until the command buffer reaches the queue.

When executed, the vertex shader emits three clip positions; clipping and rasterization find the triangle’s covered samples; the fragment shader returns green for them; the color target writes those values into the same image that was cleared blue. One pass now performs both the background clear and the triangle draw.

8.9Experiments#

These short, optional checks help you test the explanation. Predict the result first, then run the program. Restore the chapter’s baseline before continuing; later chapters start from the result taught here, without the optional changes.

  1. Change one vertex x coordinate beyond +1. Observe clipping rather than assuming the entire triangle disappears.
  2. Change the fragment output to red. Compare how this differs from changing the pass clear color.
  3. Move all vertex z values to −1, observe clipping, then restore zero. Depth clipping applies even without a depth test.

8.13Challenges#

Optional extensions. The complete game in chapter 23 requires none of these. Work in a separate copy if you want to explore; the next chapter starts from the unmodified result described here.

  1. A geometric emblem

    Expand the shader’s position array to six entries and draw two triangles that form a simple emblem. Keep every triangle inside the clip volume.

    Check your result: Both triangles appear with a draw count of six and no additional pipeline.

  2. Two color pipelines

    Create two pipelines using fragment entry points with different constant colors. Switch the selected pipeline using a key, and release both at shutdown.

    Check your result: Switching colors selects an existing pipeline instead of creating one inside the frame loop.
