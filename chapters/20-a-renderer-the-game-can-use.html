20.1The boundary follows who makes the decision#

The game knows that a room goes behind a player. The renderer knows how to turn ordered image rectangles into GPU work. Main knows when to poll events, update, and render. A useful boundary puts each decision with the code that understands its meaning, even when that means moving only a few lines.

Begin_Frame starts a CPU drawing list. Sprite appends geometry to it. End_Frame uploads and presents the result. Calling Sprite is therefore a description of a future draw, not an immediate picture update. Texture IDs identify renderer-owned assets; the game does not release native texture handles itself.

Batching groups compatible work. We only merge adjacent equal textures because draw order affects transparency. For room, player, white, white, there are three runs. Sorting by texture could move a foreground image behind the player. Preserving the requested picture is the API’s first responsibility.

20.2What still belongs in the wrong place?#

The room is visible, but main still decides that the background is drawn before the player. That is game knowledge. We now move those calls into game.Draw. This is a small refactoring, not a renderer rewrite: all GPU resources, shaders, and batching behavior introduced in chapter 19 remain unchanged. Running this checkpoint should look identical to the previous one.

20.3The contract before the call sites#

ProcedurePrecondition / inputEffect / result
Init(&r, window)Zero-initialized, stable-address State; live SDL windowCreates native/GPU resources. On false, still call Shutdown.
Load_PNG(&r, bytes)Initialized renderer, trusted bytes, outside a frameUploads once; returns stable nonzero texture ID, or zero on fatal startup failure.
Resize(&r)Renderer is aliveMarks surface configuration dirty; does not touch game state.
Begin_Frame(&r, world_size)No frame currently recording; positive finite extentStarts a fresh CPU-side sprite list. Does not acquire a surface image.
Sprite(&r, id, position, size, tint)Recording frame, renderer-owned ID, positive sizeAppends one image quad by value; preserves call order.
Rect(&r, position, size, color)Same recording contractUses the renderer’s white texture and Sprite machinery.
End_Frame(&r)Exactly one open frameUploads, encodes, submits and presents, or returns Skipped/Fatal. Closes recording on every path.
Shutdown(&r)Main thread; no more use afterwardWaits at shutdown, releases owned objects, handles partial initialization.

A returned texture ID is meaningful only in the renderer that issued it, until that renderer shuts down. The integer is not a portable asset identifier and cannot be serialized as a persistent save-game reference. The renderer owns the native resources; game.Init selects which files to load. All calls remain on SDL’s main thread. Do not copy an initialized renderer State: copying native handles does not add references, and double shutdown would release ownership twice.

Our State fields are visible in Odin source so that the implementation can be inspected. “Use the API” is a project rule, not an opaque-type guarantee. A useful review check is that game files contain no wgpu import and never access renderer internals. The included recorder tests deliberately inspect internal arrays as white-box tests; gameplay code does not. Making the type opaque later is possible but not necessary to learn or maintain this small program.

20.4Move composition, keep behavior#

In src/main.odin, remove the two Sprite calls and the local feet calculation, and remove the now-unused math import. Replace that block with game.Draw(&world, &rendering). Add the following procedure at the end of game/game.odin. The exact patch below shows both sides of this move.

The game chooses draw order and the player’s visual anchor. It asks the renderer for an image at a location, not for a command encoder. Drawing does not change world.position. The local snapped coordinate is a temporary presentation choice; the next update still starts with the unsnapped floating-point state. This separation makes a screenshot, a skipped presentation, or a future second view incapable of advancing simulation accidentally.

The order is now straightforward: pump SDL events; translate keyboard state; calculate elapsed seconds; update the world; begin a drawing list; ask the game to describe its scene; finish the frame. Main can throttle Skipped frames without asking the game to interpret surface status. Fatal errors exit to the same deferred cleanup as startup failures. Surface acquisition remains inside End_Frame, after the scene has been described; if acquisition fails recoverably, that frame’s CPU list is simply discarded.

20.5Why this batch is modest and correct#

The renderer uploads one vertex prefix, then groups only consecutive sprites with the same texture. For [room, player, white, white], the sequence has three draws. For [room, player, room], it has three draws, not two. Sorting by texture would reduce some state changes but alter painter’s order. Our alpha blend is order-dependent: a translucent later sprite sees the framebuffer color from earlier sprites. Correct composition is more important than minimizing an already tiny number of binds.

Every run binds group 1 before DrawIndexed. Group 0 and the vertex/index buffers remain selected across runs. Render-pass state is recorded, so each draw uses the state selected at that point in the command stream. CPU sprite recording and WebGPU command recording are separate stages: Sprite fills ordinary Odin arrays, while End_Frame turns those arrays into GPU data and draw commands. A command buffer is still submitted once; batching has not made rendering immediate.

This design is deliberately not a universal 2D renderer. There is one full-image UV rectangle, one blend mode, no rotation, no depth, no unloading, and fixed capacities. Those constraints make the API honest. A future atlas would add a UV rectangle because a caller actually needs a sub-image; it would not justify an asset database today. A second blend mode would need explicit ordering and pipeline rules, not an undocumented flag ignored by some draws.

20.6Ownership you can audit#

ItemOwnerLifetime
Embedded PNG bytesExecutable/static dataProcess; immutable build input.
Decoded RGBA allocationLoad_PNGOnly until QueueWriteTexture returns.
Texture, texture view, texture bind grouprenderer.State slotInitialization through Shutdown.
Sampler, pipeline, three GPU buffersrenderer.StateMany frames; no rebuild for a size-only resize.
Texture_ID in game.StateGame stores a borrowed identifierOnly while owning renderer is alive.
CPU vertex prefix and texture-ID listrenderer.StateStorage reused every frame; contents overwritten by Begin/Sprite.
Acquired surface texture/view and encoding objectsEnd_FrameOne frame; defer releases on every return path.

Shutdown polls for completion once, then releases game image groups before their views and textures, followed by the sampler, layouts, buffers, pipeline, and connection. Native reference tracking also retains dependencies as required, but an explicit readable order helps auditing. The unchanged GPU teardown includes a conservative second completion poll before surface/device destruction; it is redundant after the renderer wait, not a per-frame synchronization strategy. Never move those waits into End_Frame merely to feel safer.

One renderer instance in this program

The inherited diagnostic callback uses process-lifetime fault storage. This application initializes one renderer and exits on a device fault. The API is not advertised as restartable after device loss or as a multi-device engine service. Supporting those cases would require a different callback/state lifetime contract, not just calling Init a second time.

20.7Professional does not mean elaborate#

The useful professional habits here are explicit ownership, named units, a narrow interface, predictable failure behavior, reproducible assets, and tests at boundaries. The game can be understood without reading native surface glue. The renderer can be understood without knowing whether the current texture depicts a bed or a spaceship. Neither package needs an abstract base class, scheduler, service locator, or editor to achieve that separation.

The renderer is general enough for this project’s sprites and diagnostic rectangles, and no more. When a feature is missing, first ask whether it belongs to scene policy or GPU mechanism. “Draw the player after the room” belongs to game.Draw. “Bind the player’s texture view before its indexed draw” belongs to End_Frame. “A chair blocks the character’s feet” belongs to simulation, which we will add next.

20.10Experiments#

These short, optional checks help you test the explanation. Predict the result first, then run the program. Restore the chapter’s baseline before continuing; later chapters assume the supplied checkpoint.

  2. Record room, player, room and trace the three texture runs. Explain the final image before running.
  3. Temporarily set MAX_SPRITES to 1 and run. Confirm that exceeding the contract produces a diagnostic instead of an incomplete frame.

20.12Challenges#

Optional extensions. The complete game in chapter 23 requires none of these. Work in a separate copy if you want to explore; the next chapter starts from this chapter’s supplied baseline.

  1. A visible status indicator

    Use Rect calls in game.Draw to display a simple bar or input indicator. Keep its state in the game and draw it after the scene.

    Check your result: The indicator uses the existing white texture and changes without adding WebGPU calls to the game package.

  2. Measure batching

    Expose a read-only diagnostic count of sprites and texture runs from the renderer. Compare adjacent equal textures with an alternating sequence.

    Check your result: Your counter agrees with the actual run structure and measuring does not reorder the scene.
