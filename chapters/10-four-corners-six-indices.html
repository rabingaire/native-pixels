10.1Turn the triangle into a rectangle#

Our vertex buffer can supply positions and colors. A rectangle needs two triangles, and those triangles share two corners. An index buffer lets both triangles refer to the same stored corners.

We will store four vertex records and six indices, then replace the ordinary draw with an indexed draw. Keep the vertex layout and color shader from chapter 9. Only the geometry and the way the draw selects it need to change.

10.2One shape, two triangles#

A triangle list consumes vertex references three at a time. Drawing four sequential vertices would create only one complete triangle and leave a remaining vertex without two partners. A rectangle requires six references: three for one triangle and three for the other. We can upload six full vertex records, or upload four records and an index buffer specifying how to reuse them.

Our index order is 0,1,2 followed by 0,2,3. Corners zero and two belong to both triangles. If we move corner zero in the vertex array, both triangles use the changed position. The vertex array answers “what is each corner?” and the index array answers “which corners form each triangle?”

10.3Replace the triangle data#

In renderer.odin, replace VERTICES with four corners and add INDICES. Leave the vertex struct, vertex layout, and shader interfaces unchanged. This consistency is the point: the pipeline understands records and topology, not a hard-coded triangle asset.

In src/renderer.odin: At file scope, replace the existing VERTICES declaration and add INDICES immediately after it, before Renderer. Keep Vertex and its assertions. Complete file with surrounding code.

The first vertex is the upper-left in the current NDC arrangement. Positive y is upward at this stage, so the top corners use +0.35. We will replace these raw normalized positions with human-friendly coordinates in the next chapter. The chosen values are temporary and depend on window aspect ratio; they do not claim that the rectangle is a particular number of pixels wide.

Add index_buffer: wgpu.Buffer to Renderer, then create and upload it after the vertex buffer. Each u16 index is two bytes. Six indices occupy 12 bytes, which also satisfies the four-byte write-size requirement. Not every odd-length array of u16 values would satisfy that upload requirement without padding, even though its individual indices are legal.

In src/renderer.odin: Inside renderer_init, insert this block after the vertex-buffer QueueWriteBuffer call and before source :=. Keep the vertex-buffer setup and shader setup. Complete file with surrounding code.

The buffer usage is .Index plus .CopyDst. An index buffer and a vertex buffer share the same underlying WebGPU buffer object type; their usage flags and the commands binding them assign different roles. We do not use a special GPU allocation API called “create index buffer.” Descriptors configure the role of a general buffer.

10.4Replace the draw, not the pipeline#

DrawIndexed takes index count, instance count, first index, base vertex, and first instance. Count six means six index entries, not six unique vertices. First index zero begins at the start of the bound index stream. Base vertex zero adds nothing to each fetched index before vertex fetch. The bound index format must match the uploaded representation: reading u16 data as Uint32 would combine pairs of indices into unrelated numbers.

Keep the pipeline’s TriangleList setting and leave its strip-index format undefined. TriangleList groups each three index entries into one triangle. We are not selecting a different way of assembling connected triangles, so the existing pipeline setting remains correct.

The GPU uses an index to select a vertex record, fetches that record’s attributes, executes the vertex shader as needed, and assembles triangles in the given order. The six references do not imply six distinct stored records or guarantee exactly six hardware vertex-shader executions. Reuse is an implementation optimization behind the API’s observable behavior.

10.5Winding is a convention, not an outline#

A triangle’s winding is the order its corners appear around its perimeter. With back-face culling enabled, reversing that order can remove a triangle. We intentionally cull neither face while learning 2D coordinates. This avoids having a later y-axis flip silently hide the rectangle. It does not disable clipping; geometry outside the clip volume is still clipped.

Add the matching index-buffer release to renderer_destroy. The buffer remains unchanged for all future character frames. Moving the character will not require rebuilding its index list: the topology stays the same when the same corners are translated.
