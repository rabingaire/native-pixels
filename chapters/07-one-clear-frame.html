7.1A frame is a short-lived transaction#

Acquire means “give me the image I may render now.” A view describes access to that image. The pass declares how we use it, the encoder records commands, and finishing produces the command buffer the queue accepts. Submit makes the recorded work available for execution. Present returns the image to the window’s presentation system. These verbs describe different boundaries.

The clear is useful work even without a shader: the pass’s load operation replaces the attachment contents with a known background. Store preserves that result. This deliberately gives us the smallest visible proof of the entire presentation path before geometry introduces more possible failures.

Every acquired reference needs cleanup on both success and early return. Ending a pass finishes its recording scope; releasing its handle ends our ownership. Neither action means the GPU has completed all work. This distinction lets the CPU prepare another frame while earlier submitted work is still executing.

7.2An image for this frame#

An acquired surface texture is a handle to the image the presentation system currently makes available for rendering. The implementation manages a set or sequence of presentable images behind the surface. It may rotate backing images or wait until one becomes available. We do not cache the texture from the previous iteration: presentation ends that image’s role as our current render target.

A texture view describes how a texture’s contents will be used: which format interpretation and subresources, such as mip levels or array layers. The texture is the storage abstraction; the view is an access description. Our acquired image has one ordinary color attachment, so TextureCreateView(texture, nil) selects the default full view. The render pass uses that view, not the raw surface or native window pointer.

7.3Add a renderer with no geometry yet#

Add src/renderer.odin and its renderer_frame procedure. In main, replace the final sdl.Delay(10) with if !renderer_frame(&gpu, window) { break }. Each call now prepares and presents one complete image. The complete procedure is in this chapter’s source; we will read its three sections in order.

The refresh happens before acquisition so no old frame handle is live during reconfiguration. On optimal success we proceed. Suboptimal success still supplies a usable image; we render it and schedule reconfiguration for the next frame. Timeout or occlusion means skip briefly. Outdated means schedule reconfiguration and retry on a later iteration. Lost means the surface connection itself is no longer usable; our small program logs this and exits rather than endlessly retrying a broken connection. Generic acquisition errors are fatal here.

The deferred texture release is installed before examining the status. That guarantees cleanup for any returned handle, including unusual error paths. The view gets its own release because it is a distinct native reference. Returning from this procedure releases the frame-local objects before the next call can reconfigure the surface.

7.4Describe the pass, then record it#

Creating the command encoder allocates a recording object. The GPU has not received a draw or clear yet. The attachment descriptor says which view receives color output, how existing contents are treated, and whether results must be preserved. loadOp = .Clear initializes the entire attachment with our background. storeOp = .Store preserves the result for presentation. Loading previous contents would be meaningless for this fully redrawn frame, and discarding the result would defeat presentation.

depthSlice = DEPTH_SLICE_UNDEFINED explicitly says this is not one depth slice of a 3D texture. Zero-initialized native descriptors do not always express every intended default. This sentinel is easy to miss because our texture is two-dimensional and we have no depth buffer. The resolveTarget remains nil: there is no multisampled image to resolve. The pass’s depth/stencil and query fields also remain absent because nothing in this chapter uses them.

The pass descriptor points to one color-attachment descriptor and sets the count to one. This pointer/count pair is another native ABI boundary, not an Odin dynamic array. Both descriptors remain valid during CommandEncoderBeginRenderPass; the recording retains its own resource relationships afterward. Even with no draw calls, the clear load operation gives the pass useful work.

7.5Finish, submit, present#

RenderPassEncoderEnd closes the pass’s recording scope. It does not release the pass handle. CommandEncoderFinish closes the whole encoder and returns a command buffer. We cannot keep appending draws to that finished recording. The one-element slice passed to QueueSubmit is adapted by the binding to the native count/pointer pair. We submit that command buffer once.

The queue now has work that depends on the acquired image. SurfacePresent hands the current image back for display through the window system after its rendering dependencies. It is a separate native call; browser presentation is integrated with canvas/browser scheduling. Submit is not present, and present is not a guarantee that the monitor has already scanned out the image.

Defers run in reverse order: command buffer, pass encoder, command encoder, texture view, texture. Releasing our native command-buffer reference immediately after submission is correct: submitted work retains the backend resources it requires. We are not synchronously freeing memory that the GPU is about to read. A release is an ownership operation, not a completion fence.

7.6Use this clear as a diagnostic boundary#

We now know whether the surface connection, configuration, acquisition, command recording, queue submission, and presentation work together. Later, if the background appears but the character does not, we can begin the search in geometry, pipeline, bindings, or shader code. That does not prove every presentation path is infallible, but it removes a large part of the startup chain from the first hypothesis.

7.11Challenges#

Optional extensions. The complete game in chapter 23 requires none of these. Work in a separate copy if you want to explore; the next chapter starts from this chapter’s supplied baseline.

  1. A keyboard palette

    Use discrete key events to select among three clear colors. Store the choice on the CPU and supply it to the next render pass.

    Check your result: The background changes while the same window, device, and surface stay alive.

  2. Count visible progress

    Add separate counters for attempted frames, successful presents, and skipped acquisitions. Print a summary at shutdown.

    Check your result: A temporarily occluded window can increase attempts without falsely counting every attempt as a presented image.
