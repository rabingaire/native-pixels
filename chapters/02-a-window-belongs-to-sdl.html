2.1Read the Odin notation as you meet it#

In these listings, name :: proc(...) { ... } declares a procedure, while value := expression creates a local variable with an inferred type. A package groups source files that compile together. An import such as sdl gives us a name for another package’s declarations. A leading dot such as .VIDEO lets the surrounding type determine which enum member we mean.

An event loop is a repeated conversation with the operating system: collect pending events, decide whether to continue, then do this iteration’s work. The window persists because the process keeps running that loop. Drawing will become another part of the loop later; an empty loop still has to process close and focus events.

defer registers work to run when the current scope exits, including an early return. If SDL initialization succeeds and window creation fails, the SDL cleanup still runs. If both succeed, the later window cleanup runs first. Think of each successful acquisition as adding one matching cleanup obligation.

2.2Two responsibilities, one application#

SDL is our connection to the desktop. It creates a native window, manages its event queue, and reports keyboard state. WebGPU will manage GPU resources and render into images associated with that window. Creating an SDL window does not create a WebGPU surface or device. Conversely, creating a WebGPU device does not create a desktop window.

SDL ownsWebGPU owns
Window and platform handlesSurface wrapper and presentation configuration
Input and window eventsBuffers, textures, shaders, pipelines
Logical and drawable window dimensionsCommands that render into drawable images
Timing queriesAsynchronous execution of submitted work

SDL also exposes a 2D renderer and an SDL GPU API. We use neither. Importing vendor:sdl3 makes many declarations available, but only the window, events, keyboard, timer, and platform-property calls belong in our application. There will be no SDL_RenderPresent or OpenGL swap call at the end of a frame.

2.3Replace the probe with a living window#

Replace src/main.odin in full. The program is short enough to see the entire lifetime before we divide it into graphics procedures.

sdl.Init({.VIDEO}) initializes the video subsystem and the event facilities it requires. SDL3 returns a boolean here: true means success. Older SDL2 examples often compare an integer result with zero. That check reverses the meaning if copied carelessly into SDL3. On failure, GetError() supplies a useful diagnostic.

All window work runs on the main thread. The platform-specific .METAL flag prepares the macOS window for a Metal view. It does not tell us to write Metal shaders or submit Metal commands: wgpu-native will use Metal internally. Other desktop platforms need no graphics-specific window flag for the surface paths in this book. We deliberately delay resizing and high-density window flags until the coordinate model is ready.

After creation, we explicitly show the window and request that SDL raise it. A desktop compositor may initially consider a background-launched window occluded; requesting foreground visibility makes interactive startup more predictable. The desktop can deny focus, so a failed raise is reported without aborting. A failed show leaves no usable visible application and returns through cleanup. Later acquisition code still handles temporary occlusion because visibility can change at any time.

CreateWindow returns an SDL-owned opaque window object that our application must eventually destroy. The title literal is passed as a cstring because SDL expects a terminated native string. Later WebGPU labels use Odin strings through wgpu.StringView, which carries a pointer and length. These are two different interop contracts; do not cast arbitrary unterminated text into a cstring.

2.4Events keep the window alive#

The inner loop drains all currently queued events. Polling also pumps SDL’s platform event machinery. The Event union carries different payloads depending on its type; this chapter only needs the tag. A quit request or close request flips a local flag. The outer loop checks that flag before starting any more work.

#partial switch is intentional: SDL defines far more event types than we need. Ignoring an unrelated mouse motion does not mean it remains queued forever; polling has already removed it. A single if PollEvent per frame can leave a backlog during an event burst. Draining the queue gives us the latest state before updating the application.

Delay(10) sleeps for roughly ten milliseconds so this empty loop does not consume an entire CPU core. It is temporary pacing, not a graphics clock. Once presentation exists, FIFO presentation normally provides backpressure, and only suspended/skipped-frame paths retain a short delay. The native title bar and client area may appear blank, black, or platform-colored here. SDL has not drawn our background; this checkpoint makes no claim about client-area pixels.

2.5Destruction follows dependency order#

The two defer statements establish reverse-order cleanup. The window is destroyed before SDL quits. An early return after a failed window creation still shuts down the successfully initialized subsystem. No failed handle is passed to its destroy function. We will extend the same pattern: drawing resources release before the device, the surface before its native view, and the native view before the window.

Descriptors are coming

This chapter uses a direct window-creation call. WebGPU will often take a pointer to a descriptor instead. A descriptor is ordinary CPU memory describing an object to create; it is not itself a GPU allocation. Keeping that distinction clear makes the next few chapters much easier.

2.8Experiments#

These short, optional checks help you test the explanation. Predict the result first, then run the program. Restore the chapter’s baseline before continuing; later chapters assume the supplied checkpoint.

  1. Change the title and dimensions, then observe that no WebGPU setup changes: neither exists yet.
  2. Temporarily increase the delay to 250 ms. Closing the window becomes noticeably sluggish because the next event pump is delayed. Restore 10 ms.

2.10Challenges#

Optional extensions. The complete game in chapter 23 requires none of these. Work in a separate copy if you want to explore; the next chapter starts from this chapter’s supplied baseline.

  1. A keyboard exit

    Handle an Escape key-down event alongside the close event. Use the existing running flag so both actions take the same cleanup path.

    Check your result: Both Escape and the title-bar close control exit cleanly.

  2. A focus-aware title

    Handle focus gain and loss events and update the window title to reflect whether the window is active.

    Check your result: Switching to another application and back changes the title without creating another window.
