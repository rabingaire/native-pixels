12.1Send the transform instead of rewriting the corners#

Chapter 11 showed the full coordinate calculation on the CPU. The local square does not change when its position changes. We will keep those corners in the vertex buffer and send position, size, view size, camera, and tint separately.

A uniform buffer holds these shared shader inputs. We will first lay out its bytes, then connect it to the shader, and finally move the existing arithmetic into WGSL. The picture should stay the same; the responsibility for transforming corners changes.

12.2What changes and what stays the same#

The unit-square vertices and six indices never change when our character moves. Only position, size, view extent, camera offset, and tint vary. Rather than rewrite vertex records, we can provide those few values through a uniform buffer: a GPU-readable resource whose values are shared by shader invocations for a draw.

“Uniform” describes how the shader accesses this data, not a claim that the bytes can never change. We will write fresh values each frame. The pipeline’s resource contract remains fixed, the bind group continues to refer to the same buffer, and the buffer contents change. This distinction is the practical reason WebGPU separates layouts, bindings, and resources.

12.3Specify the host/shader memory contract#

Add Uniforms and its assertions in renderer.odin. Add the corresponding WGSL struct at the top of the shader, before Vertex_Out. Unlike the vertex layout, uniform memory layout is defined by WGSL’s host-shareable type rules, not by an array of vertex attributes.

Alignment is a rule about where a value may start in memory. If a field needs 16-byte alignment, its offset within this block must be a multiple of 16. Padding is unused space inserted to satisfy such rules. Our four pairs occupy bytes 0 through 31, leaving the four-component tint correctly aligned at byte 32. The table below checks every field.

The four vec2f fields use 32 bytes, and the vec4f tint uses 16 more, making 48. Odin’s #align(16) gives the host struct the required alignment. The size and offset assertions check that its memory matches the WGSL struct. When changing a field’s type, recalculate both layouts before uploading the new data.

There is also an alignment rule for the start of a uniform buffer binding. Our binding begins at byte zero, which satisfies it. We can allocate exactly 48 bytes for this block; we do not need to round the allocation up to 256. Member offsets inside the struct and the start of the buffer range are separate checks.

12.4Describe the interface, then attach actual storage#

Add uniform_buffer and bind_group handles to Renderer. In renderer_init, replace the empty pipeline-layout construction with this sequence. The shader module already exists at this point; the final render pipeline is created afterward.

Consider the shader declaration @group(0) @binding(0). It requests one numbered resource slot. The bind group layout describes what that slot accepts: a uniform buffer readable by the vertex shader, with at least 48 bytes. The bind group fills that slot with our actual buffer. The pipeline layout puts that group layout at group number zero. These descriptions let WebGPU check that the shader and the supplied buffer agree before drawing.

The layout entry’s binding = 0 matches WGSL @binding(0). Vertex visibility means the vertex stage may read it; our fragment stage consumes the interpolated tinted color instead of directly accessing the buffer. The entry’s buffer type is Uniform, with a minimum binding size of 48. The bind group then attaches the actual buffer at byte offset zero with range 48. It does not copy the uniform bytes or freeze their current value.

The pipeline layout contains one layout at array position zero, which matches @group(0). That position is the group number; it is not the binding number within the group. Both happen to be zero because we have exactly one of each. If the interface is wrong, pipeline validation or draw validation can reject the shader/resource combination before it accesses arbitrary memory.

12.5Move the arithmetic, preserve the result#

Remove the temporary CPU vertex transform and its per-frame vertex upload. Replace that section of renderer_frame with a uniform value and write. The one-time vertex upload in renderer_init stays; it now holds unit-square local positions for every frame.

WGSL now performs the same multiply/add and pixel-to-NDC conversion as the previous CPU code. Subtracting camera defines a simple translation-only camera: if the camera moves right, a stationary world object appears farther left. Its default is (0,0). The multiply, add, and subtract operations express the transform we need.

Immediately after setting the pipeline, add RenderPassEncoderSetBindGroup(pass, 0, renderer.bind_group). The call binds actual resources to group zero for the upcoming draw. Native descriptor pointers can expire after creation, but the returned bind group and the uniform buffer must remain usable for subsequent frames. Release the bind group and buffer in renderer_destroy. Our references to the group layout and pipeline layout can be released at the end of initialization.

12.6One write does not wait for one draw#

QueueWriteBuffer orders the data update before the next submission on that queue. Reusing this uniform buffer across successive frames is valid under that ordering. Do not insert a GPU-wide wait just to “make sure the new position arrived.” Conversely, writing two object transforms before a single submission does not make two draws automatically remember different versions: both draws can observe the last data written before them in queue order. For two objects, separate uniform buffers and bind groups would give each draw its own values. We will solve the multiple-object problem when the project needs it. For this chapter there is one draw and one update.

12.13Challenges#

Optional extensions. The complete game in chapter 23 requires none of these. Work in a separate copy if you want to explore; the next chapter starts from the unmodified result described here.

  1. A scrolling camera

    Use the existing camera field to pan the view with separate keys. Leave character position unchanged and upload the camera through the same uniform buffer.

    Check your result: Panning affects projection while game coordinates retain their meaning.

  2. Two independent characters

    Create a second uniform buffer and bind group with the same layout, then bind each before its draw. Give the characters different positions and tints.

    Check your result: Both characters keep independent transforms; writing one shared buffer twice before submission is not used as a substitute.
