12.1A layout is a promise; a binding fills it#

A uniform buffer stores a small block of values shared by a draw’s shader invocations. The bind group layout describes the permitted contents of numbered slots. A bind group fills those slots with actual resources. The pipeline layout arranges groups into the interface the shader expects. Creating these objects does not upload position values; QueueWriteBuffer does that separately.

Our shader reads group zero, binding zero. That slot refers to a 48-byte range in a persistent uniform buffer. Updating the position bytes changes the next draw’s input while the group continues to refer to exactly the same storage. We do not recreate a mailing address each time the contents at that address change.

Alignment means a value must begin at an address divisible by a required number of bytes. The layout table makes the host and shader agree. Buffer-binding offset alignment is a separate constraint; our range starts at zero, which meets any positive alignment requirement. A valid 48-byte struct does not automatically need a 256-byte allocation.

12.2What changes and what stays the same#

The unit-square vertices and six indices never change when our character moves. Only position, size, view extent, camera offset, and tint vary. Rather than rewrite vertex records, we can provide those few values through a uniform buffer: a GPU-readable resource whose values are shared by shader invocations for a draw.

“Uniform” describes how the shader accesses this data, not a claim that the bytes can never change. We will write fresh values each frame. The pipeline’s resource contract remains fixed, the bind group continues to refer to the same buffer, and the buffer contents change. This distinction is the practical reason WebGPU separates layouts, bindings, and resources.

12.3Specify the host/shader memory contract#

Add Uniforms and its assertions in renderer.odin. Add the corresponding WGSL struct at the top of the shader, before Vertex_Out. Unlike the vertex layout, uniform memory layout is defined by WGSL’s host-shareable type rules, not by an array of vertex attributes.

MemberOdin bytesWGSL alignment / size
position0–7vec2f: align 8, size 8
size8–15vec2f: align 8, size 8
view_size16–23vec2f: align 8, size 8
camera24–31vec2f: align 8, size 8
tint32–47vec4f: align 16, size 16
Whole struct48 bytes, host alignment 16Struct extent rounded to its required alignment

The four vec2f members pack into the first 32 bytes, then the vec4f tint occupies 16 more. Odin’s #align(16) and the explicit offset/size assertions document the exact layout we upload. A vec3f is a classic source of mistakes because its alignment and payload size differ; we need no vec3f here. Replacing a field with another type requires recalculating offsets on both sides, not merely matching member names.

A buffer binding’s offset alignment is another rule, separate from member layout. Our binding starts at offset zero, so it satisfies the device’s uniform-offset alignment without padding the buffer to 256 bytes. A 48-byte uniform allocation is valid. If we later packed multiple objects into one buffer and selected aligned ranges, the start of each binding could need padding to the device’s minUniformBufferOffsetAlignment. That is not needed for one character.

12.4Describe the interface, then attach actual storage#

Add uniform_buffer and bind_group handles to Renderer. In renderer_init, replace the empty pipeline-layout construction with this sequence. The shader module already exists at this point; the final render pipeline is created afterward.

ObjectQuestion it answersDependency
Uniform bufferWhere do the 48 bytes live?Device
Bind group layoutWhich binding numbers, resource kinds, visibility, and minimum sizes are permitted?Device and shader contract
Bind groupWhich actual buffer/range fills binding zero?Layout plus uniform buffer
Pipeline layoutWhich bind group layout is group zero?Ordered list of bind group layouts
Render pipelineWhich shaders and fixed state use that resource interface?Pipeline layout, shader stages, target configuration

The layout entry’s binding = 0 matches WGSL @binding(0). Vertex visibility means the vertex stage may read it; our fragment stage consumes the interpolated tinted color instead of directly accessing the buffer. The entry’s buffer type is Uniform, with a minimum binding size of 48. The bind group then attaches the actual buffer at byte offset zero with range 48. It does not copy the uniform bytes or freeze their current value.

The pipeline layout contains one layout at array position zero, which matches @group(0). That position is the group number; it is not the binding number within the group. Both happen to be zero because we have exactly one of each. If the interface is wrong, pipeline validation or draw validation can reject the shader/resource combination before it accesses arbitrary memory.

12.5Move the arithmetic, preserve the result#

Remove the temporary CPU vertex transform and its per-frame vertex upload. Replace that section of renderer_frame with a uniform value and write. The one-time vertex upload in renderer_init stays; it now holds unit-square local positions for every frame.

WGSL now performs the same multiply/add and pixel-to-NDC conversion as the previous CPU code. Subtracting camera defines a simple translation-only camera: if the camera moves right, a stationary world object appears farther left. Its default is (0,0). A matrix is still unnecessary because scale and translation remain compact and obvious. Rotation or many composed transforms could justify matrices later; this project does not need them.

Immediately after setting the pipeline, add RenderPassEncoderSetBindGroup(pass, 0, renderer.bind_group). The call binds actual resources to group zero for the upcoming draw. No dynamic offsets are supplied. Native descriptor pointers can expire after creation, but the returned bind group and the uniform buffer must remain usable for subsequent frames. Release the bind group and buffer in renderer_destroy. Our references to the group layout and pipeline layout can be released at the end of initialization.

12.6One write does not wait for one draw#

QueueWriteBuffer orders the data update before the next submission on that queue. Reusing this uniform buffer across successive frames is valid under that ordering. Do not insert a GPU-wide wait just to “make sure the new position arrived.” Conversely, writing two object transforms before a single submission does not make two draws automatically remember different versions: both draws can observe the last data written before them in queue order. Multiple objects would need distinct ranges, dynamic offsets, or another explicitly ordered strategy. We have one draw and one update.

Why no storage buffer?

A storage buffer can expose larger arrays or writable shader data, but our shader needs a tiny read-only parameter block. Uniforms are sufficient. Adding storage here would teach a feature without solving a problem the character has.

12.11Challenges#

Optional extensions. The complete game in chapter 23 requires none of these. Work in a separate copy if you want to explore; the next chapter starts from this chapter’s supplied baseline.

  1. A scrolling camera

    Use the existing camera field to pan the view with separate keys. Leave character position unchanged and upload the camera through the same uniform buffer.

    Check your result: Panning affects projection while game coordinates retain their meaning.

  2. Two independent characters

    Create a second uniform buffer and bind group with the same layout, then bind each before its draw. Give the characters different positions and tints.

    Check your result: Both characters keep independent transforms; writing one shared buffer twice before submission is not used as a substitute.
