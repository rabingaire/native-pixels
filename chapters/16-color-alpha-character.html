16.1Give the moving rectangle a face#

The character moves at a speed measured in seconds and stays inside the view. It is still a colored rectangle. We will use its local coordinates to select small eye and mouth regions in the fragment shader.

We will also introduce alpha blending, the rule for combining the character’s color with the existing background. We will work through the color calculation before choosing blend factors in the pipeline.

16.2A recognizable character needs very little art#

Our application already meets the movement goal. We will add a face without introducing texture loading, sampling, or an asset pipeline. The local unit-square coordinates give each fragment a useful location within the character. The fragment shader can test a few small rectangles for eyes and a mouth and choose a dark color for those regions.

This is still triangle rendering. The face does not create more vertices or separate draw calls. The rasterizer covers the same two triangles, while the fragment shader chooses different colors within their coverage. The GPU’s geometry and coloring responsibilities are now especially easy to distinguish.

16.3Pass local position through the rasterizer#

In shaders/character.wgsl, add @location(1) local_position: vec2f to Vertex_Out. In vs_main, assign out.local_position = position before returning. This is the original local position from the vertex buffer, not the clip position. The rasterizer interpolates it across the rectangle, producing values approximately in [0,1] inside the character.

The eye and mouth tests operate in character-local fractions, so the features follow position and scale automatically. At x=0.29 and y=0.32, for example, a fragment lies inside the left eye. A fragment at the center of the body falls through to the interpolated body color. Because both triangles agree on local corner values, the diagonal does not interrupt the face.

The dark face color uses the same alpha as the body. If we later make the character partially transparent, the eyes and mouth remain part of the same opacity convention. These tests have hard edges at single-sample coverage; we do not claim they provide analytic antialiasing. The aim is a simple recognizable figure, not a shader-art system.

16.4Alpha is an input to a composition rule#

An alpha value of 0.5 does not inherently mean “show half the background.” With blending disabled, writing RGBA (green,0.5) can replace the previous target value, including its alpha. To combine the character color with the cleared background, the pipeline must enable a blend state.

We use straight alpha: the shader’s RGB values are unmultiplied colors, and alpha separately describes their opacity. For source color Cs, destination color Cd, and source alpha As, the RGB equation is Cs × As + Cd × (1 − As). The output alpha is As + Ad × (1 − As). The background starts with alpha one, so the resulting window image remains alpha one.

For example, take a red source (1,0,0) with alpha 0.5 over opaque blue (0,0,1). Half the source plus half the destination gives linear RGB (0.5,0,0.5). The output alpha stays 1. The blend descriptor below expresses those same multiplications and addition; its color and alpha factors differ because the two equations differ.

The color and alpha components have different source factors. Multiplying source alpha by itself would give As² rather than As in the alpha equation. Premultiplied alpha would instead supply RGB already multiplied by alpha and normally use source factor One for color too. Both conventions can work; mixing straight shader output with premultiplied blend factors gives the wrong result.

Blending is part of the pipeline because it affects output compatibility and fixed backend state. The descriptor’s blend pointer is local CPU input read during pipeline creation. Changing a local BlendState after the pipeline was created does not mutate that pipeline. Changing the character’s tint alpha, on the other hand, changes uniform data and needs no new pipeline.

16.5Color encoding does not replace blending#

Our surface target is sRGB. The shader works with linear RGB values; the attachment handles sRGB storage conversion. Blend calculations use the appropriate linear color values. If you put a familiar sRGB display value such as 0.5 directly into the shader, you are specifying linear 0.5, which displays much brighter than an sRGB-encoded 0.5 swatch. For these chosen geometric colors, we define the numbers as linear from the outset.

Surface composite alpha remains separate: it controls the whole window image’s relationship with the desktop compositor. Our opaque background ensures that window image is opaque. The character’s blend alpha only combines it with pixels already in our own attachment. You can make the character translucent without making the desktop visible through the window.

Ordering matters when transparent objects overlap. A source-over blend can give a different result when you reverse draw order. We have one character over a cleared background, so the order is completely explicit and no sorting system is needed. The internal shared triangle edge follows rasterization coverage rules; it is not two full-opacity layers painted on top of each other.

16.6Check the face and opacity separately#

Build and run with the normal tint alpha of 1. The eyes and mouth should move with the body. Then temporarily change the initial tint alpha in main to 0.5. The background should show through the entire character, including the face. Restore alpha 1 before continuing. This separates a coordinate error, where the face moves incorrectly, from a blending error, where opacity behaves incorrectly.
