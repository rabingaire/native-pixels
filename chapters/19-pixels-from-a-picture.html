19.1Trace one picture through memory#

A PNG file is compressed bytes. Decoding expands those bytes into a CPU array of pixels. Uploading copies that data into a GPU texture. A texture view exposes the image to a shader, and a sampler decides which texel to read for a texture coordinate. A texel is a pixel in a texture; it does not have to correspond one-to-one with a window pixel.

The room image is 1536 × 1024 texels but occupies 384 × 256 world units. That is four source texels per world unit. A 768 × 512 framebuffer displays the world at two physical pixels per unit, so source texels are still being reduced. Nearest sampling chooses a texel without blending its neighbors; it does not turn high-resolution generated art into a perfectly uniform low-resolution tileset.

This chapter changes several connected contracts. Read it in passes: first file layout and image loading, then shader inputs and bindings, then sprite recording and presentation. Compare each pass with the complete files below. Chapter 20 moves composition into game.Draw, so main temporarily contains those two scene calls here.

19.2A deliberate extension of the destination#

Chapter 18 completed our graphics foundation. Now we will use it to make a small top-down room: a bed, bedside table, bookshelf, work table and chair, chest, plant, and a character who can walk between them. This extension teaches production habits at a small scale: a stable renderer interface, explicit asset ownership, separate simulation and drawing, collision tests, and useful diagnostics. It is not a detour into an engine framework. The earlier 18 checkpoints remain unchanged and independently runnable.

This chapter is the largest migration in the extension. Read the upload and shader sections first, then the batching and frame sections. Each explains a specific portion of the complete replacement renderer. We reuse the already understood native surface/device code without hiding it in a third-party helper. Chapter 20 will finish moving scene composition out of main and examine the resulting contract.

The supplied room is 1536 × 1024 RGB; the player is 1254 × 1254 RGBA with genuine transparency. Both were generated with the built-in image-generation tool, then preserved as PNG files. The exact generation prompts are included. The game does not call an image-generation service. These are checked-in build inputs, just like WGSL.

Pixel-art style versus a pixel-grid specification

These generated assets have chunky pixel-art styling; they are not a rigorously hand-authored 384 × 256 tileset or a 32 × 32 sprite sheet. We preserve their original pixels and sample with nearest filtering. That gives a crisp presentation, but high-resolution source details can differ with display scale. A strict retro raster would use assets authored to one low-resolution grid, or an offscreen low-resolution render target followed by nearest upscaling. Neither is silently claimed here.

19.4A PNG is not a texture#

A PNG is compressed file data on the CPU. A WebGPU texture is device-owned, typed image storage, usable only in ways permitted by its usage flags. A texture view selects how shaders or attachments access that storage. A sampler is a separate object specifying how texture coordinates choose texels. These are four different things; none substitutes for the others.

Add this procedure in renderer/texture.odin. vendor:stb/image is the pinned Odin distribution’s native image decoder binding; it introduces no new downloaded library and hides no WebGPU calls. #load(..., []u8) in game.Init embeds the PNG bytes at compile time, so launching from a different working directory still works. Changing a PNG requires rebuilding. This simple asset policy is intentional, not a runtime asset manager.

The native decoder accepts a many-pointer and C integer byte count. The length checks prevent truncating that count. The header query checks positive dimensions against the actual device limit before allocating decoded pixels. The final argument 4 asks for four output channels even though the room file has only three; the decoder supplies opaque alpha. channels describes the source file, not the requested output stride. The returned allocation belongs to the decoder and is freed with image_free, never Odin’s general delete. These are trusted embedded assets, not an untrusted file-upload service with a complete memory-budget defense.

The texture descriptor allocates one 2D, single-sample image with one mip level and one layer. RGBA8UnormSrgb stores four 8-bit normalized channels and decodes sRGB color to linear values when sampled; alpha remains linear. TextureBinding permits shader sampling. CopyDst permits the upload. It is not a render attachment and does not need that permission. Its format need not equal the window’s BGRA surface format: sampling produces a shader value, and the pipeline writes that value to the differently formatted attachment.

The destination identifies texture, level zero, origin zero, and all color aspects. The data layout describes CPU bytes: row zero starts at offset zero, each row has width × 4 bytes, and there are height rows. The extent describes the region being written. QueueWriteTexture accepts tightly packed rows; the 256-byte row-pitch rule for buffer-to-texture command copies does not apply to this queue upload. Our 1254-pixel player has a 5016-byte row, which deliberately exercises that distinction. WebGPU’s writeTexture contract describes this separate upload path.

The call consumes/copies the CPU data for the upload before returning; it does not promise that GPU work has finished. We can free decoded pixels afterward because the implementation owns the queued transfer. Subsequent submissions to this queue observe the earlier texture writes. We do not poll the GPU after each upload.

The renderer retains the texture, view, and concrete bind group in one slot. A successful load returns a distinct integer Texture_ID; zero means failure. The game holds that ID, not a native texture reference. No slots are recycled: all assets live until renderer shutdown. A failed startup immediately takes the shutdown path, which visits even partially initialized slots. Do not add “retry load” semantics without first cleaning a failed slot.

19.5Two groups, two responsibilities#

WGSL addressOdin resourcePurpose
@group(0) @binding(0)view_buffer through view_groupWorld extent shared by every sprite in the frame.
@group(1) @binding(0)Texture_Slot.viewThe sampled room, player, or white texture.
@group(1) @binding(1)State.samplerNearest filtering and clamped UV addressing.

Inside renderer.Init, the texture layout declares a filterable floating-point 2D image and a filtering-compatible sampler, both visible only to the fragment stage. “Filtering” here is an allowed binding class, not a command to interpolate neighboring pixels. The concrete sampler chooses Nearest for minification and magnification. ClampToEdge prevents wrapping across UV boundaries. Mip clamps and a single texture level keep the sampling policy explicit.

The pipeline layout receives the view layout first and the texture layout second, matching group indices 0 and 1. Every loaded image gets a bind group conforming to the same texture layout. Switching images therefore requires changing group 1, not creating another pipeline. The pipeline’s target still matches the acquired surface view; the texture input format belongs to a different side of the pipeline.

19.6The new vertex contract#

Odin memoryVertex layoutWGSL vertex input
position: [2]f32, bytes 0–7Float32x2, offset 0, location 0@location(0) position: vec2f
uv: [2]f32, bytes 8–15Float32x2, offset 8, location 1@location(1) uv: vec2f
tint: [4]f32, bytes 16–31Float32x4, offset 16, location 2@location(2) tint: vec4f
Next vertex begins 32 bytes laterarrayStride = 32, stepMode = VertexOne complete input record per indexed vertex

Replace the old 24-byte position/color vertex with this 32-byte record. A UV is a pair of texture coordinates: (0,0) addresses the top-left end of the image and (1,1) the bottom-right end. The four corners of each quad receive those coordinates. Rasterization interpolates them across the triangles, letting each fragment sample the appropriate part of the picture. Shader output location 0 carries UV to fragment input location 0; it does not need to match the vertex attribute’s location 1. Locations connect a particular pair of pipeline stages, not a globally named property.

The vertex shader receives already positioned world-space corners. The CPU expands each sprite rectangle; the shader applies the same world-to-NDC conversion we already know. We removed per-character transform uniforms because position now belongs to each vertex record. The 16-byte view uniform contains a vec2 extent and an explicit vec2 padding field; Odin alignment and size assertions match WGSL.

The fragment shader’s textureSample reads filtered-by-the-sampler color and multiplies it by a linear tint. The PNG decoder produces straight-alpha pixels, and the existing straight-alpha blend factors are retained. An alpha-zero fragment contributes no source RGB to the framebuffer. Do not multiply RGB by alpha in this shader unless you also switch to a premultiplied-alpha blend convention. The surface’s sRGB format encodes the linear blended result for display.

19.7Recording more than one rectangle#

Add Sprite to the renderer API. Between Begin_Frame and End_Frame, it writes four CPU-side vertices and one texture ID into fixed-capacity arrays. Nothing has reached the GPU yet. The room is submitted first and the player second. Their positions are independent because each sprite has its own vertex bytes; repeatedly updating a single transform uniform before one submission would instead make all draws read the final value.

Init creates one vertex buffer large enough for 256 quads, plus a static index buffer containing the familiar 0,1,2,0,2,3 pattern with four added per sprite. The maximum vertex index is 1023, safely within Uint16. End_Frame uploads only the used vertex prefix and one view uniform. It scans adjacent equal texture IDs into runs, binds that texture group, and calls DrawIndexed with firstIndex = first × 6. Indices already refer to absolute vertices, so baseVertex remains zero. Read the complete Init and End_Frame listings below alongside this paragraph; no batching library performs these steps for us.

A bounded API should fail visibly

Eight texture slots include one internal white pixel, leaving seven for game images. A frame holds 256 sprites, including debug rectangles. Invalid IDs and excess sprites set a flag; End_Frame reports Fatal before uploading. Capacity is a project constraint, not an invitation to silently drop draws. There are no per-frame heap allocations in our sprite recorder.

19.8Fit a room, do not resize the world#

Replace the window-sized game extent with 384 × 256 world units. The renderer queries physical framebuffer dimensions, chooses the smaller axis scale, rounds it down to a whole number when at least one-times scale fits, and centers a viewport. Very small windows use a fractional fit instead of cropping. Clear still initializes the entire attachment, producing dark letterbox bars. The scissor bounds writes to the viewport region; the viewport transforms coordinates, while the scissor rejects output samples outside a rectangle. Both reset with each new render pass, so both are set each frame.

The room occupies the complete world rectangle. The player’s whole transparent canvas occupies 32 × 32 units. Its visible artwork uses only part of that canvas, so {16,30} is an authored anchor near the boots, not half the visible character’s height. We round the displayed feet position, then subtract this anchor. Simulation retains fractional movement. This avoids accumulating rounding error and establishes the foot point we will use for collision.

19.11Experiments#

These short, optional checks help you test the explanation. Predict the result first, then run the program. Restore the chapter’s baseline before continuing; later chapters assume the supplied checkpoint.

  1. Tint the player {1, 0.5, 0.5, 1}; leave the room white. Observe that texture color is multiplied, not replaced.
  2. Draw the player before the opaque room. Explain why it disappears without blaming the upload.
  3. Make the window narrower than 384 physical pixels; compare fractional fitting with the normal integer-scale viewport.

19.13Challenges#

Optional extensions. The complete game in chapter 23 requires none of these. Work in a separate copy if you want to explore; the next chapter starts from this chapter’s supplied baseline.

  1. A decoration layer

    Draw an additional tinted or translucent decoration using an existing texture or the renderer’s white rectangle. Choose its place in painter’s order explicitly.

    Check your result: The decoration appears in front of or behind the player as intended and does not upload texture pixels every frame.

  2. An image-size diagnostic

    Display or log source texel dimensions, chosen world size, and current viewport scale for an asset.

    Check your result: You can explain an image’s apparent size without treating its PNG dimensions as game coordinates.
