19.1Use pictures for the room and player#

The moving geometric character has taught us buffers, shader inputs, coordinate conversion, and blending. We now need two pictures in one frame: a room behind a player. The renderer must keep their positions and image choices separate.

This chapter has several connected steps. Start with why we need a list of sprites and separate packages. Then learn image coordinates and shader bindings, upload the image bytes, record the two rectangles, and fit the fixed room into the window. Each step below has its own code and explanation; assemble the complete files before running.

19.2Add the room artwork#

Our geometric character already moves in a native window. Now we will use pictures for its appearance and surroundings. The room image contains a bed, tables, bookshelf, chair, chest, and plant. The player will move over that image using the same input and seconds-based update we already wrote. In this chapter the furniture is only painted scenery; collision comes after drawing the room works.

We will reuse the native window, surface, device, and frame-lifetime code. The drawing data changes because we need a background and a player with different images and positions. Work through the sections in order. They explain the replacement renderer in parts, and the complete file listings at the end put those parts together.

The room contains 1536 × 1024 source pixels. The player image is 1254 × 1254 and includes an alpha channel for transparent surroundings. Both PNG files are included as book attachments. Create an assets directory beside src, then save room.png and player.png there. Save the original files, not screenshots of their previews; screenshots may discard transparency. The application will embed these images when it builds.

The artwork has a pixel-art style, but its source pixels do not form a uniform low-resolution game grid. Nearest sampling, introduced below, keeps neighboring texels from blending together. It cannot repair uneven detail in an image. We will keep the source images unchanged and choose their displayed size in world units.

19.3Give two pictures independent drawing data#

Our old renderer draws one rectangle using one position uniform. The room needs two rectangles in the same frame: a background covering the world and a smaller player on top. Writing that one uniform twice before submitting would leave both draws reading the final contents. We need separate position data for each rectangle.

We will store four positioned vertices per picture in one CPU array, then upload the used part once. A picture drawn on a rectangle is called a sprite. Sprite will append its corners and record which image to use. Begin_Frame starts an empty list; End_Frame turns the list into the GPU commands we already understand. These procedures solve the two-picture problem before the game gains more objects.

The renderer now needs a file for image loading as well as the existing surface, device, and drawing files. Give those files their own renderer directory and package. The game gets a game directory. A relative import such as import renderer "../renderer" means “find that directory beside this one.” renderer.State then names the State type in that package.

Files in the same directory share package declarations, but each file declares its own imports. The application’s src directory will contain only main.odin. We keep the old GPU and platform procedures inside the renderer package; their behavior does not change. The file table below gives every move and replacement.

A texture ID is an integer identifying one image owned by this renderer. We use Texture_ID :: distinct u32 to give IDs their own type. Zero means loading failed; successful IDs start at one. Keeping the native texture and its cleanup inside the renderer means game code can choose an image without managing GPU handles.

19.5Choose a point in a picture#

A PNG file stores a compressed image. Decoding expands it into pixels in CPU memory. Uploading copies those pixels to a GPU texture. A texel is one pixel in a texture; it need not cover exactly one window pixel. For example, the 1536 × 1024 room will occupy 384 × 256 world units, so there are four source texels along each world unit.

UV coordinates select a point in a texture. U runs left to right and V runs top to bottom. Both run from 0 to 1 across the whole image. The upper-left corner uses (0,0), the lower-right uses (1,1), and the center uses (0.5,0.5). Four UV corners on the rectangle let rasterization find a coordinate for each covered fragment.

A texture view gives the shader access to the image, and a sampler determines how a UV coordinate chooses a texel. We choose nearest filtering: read the nearest texel instead of blending its neighbors. ClampToEdge holds coordinates at the image edge instead of repeating the picture. We use one full-resolution image level, called mip level zero; there are no smaller precomputed versions.

Inside renderer.Init, the texture layout declares a filterable floating-point 2D image and a filtering-compatible sampler, both visible only to the fragment stage. “Filtering” here is an allowed binding class, not a command to interpolate neighboring pixels. The concrete sampler chooses Nearest for minification and magnification. ClampToEdge prevents wrapping across UV boundaries. Mip clamps and a single texture level keep the sampling policy explicit.

The pipeline layout receives the view layout first and the texture layout second, matching group indices 0 and 1. Every loaded image gets a bind group conforming to the same texture layout. Switching images therefore requires changing group 1, not creating another pipeline. The pipeline’s target still matches the acquired surface view; the texture input format belongs to a different side of the pipeline.

The vertex shader receives already positioned world-space corners. The CPU expands each sprite rectangle; the shader applies the same world-to-NDC conversion we already know. We removed per-character transform uniforms because position now belongs to each vertex record. The 16-byte view uniform contains a vec2 extent and an explicit vec2 padding field; Odin alignment and size assertions match WGSL.

The fragment shader’s textureSample reads filtered-by-the-sampler color and multiplies it by a linear tint. The PNG decoder produces straight-alpha pixels, and the existing straight-alpha blend factors are retained. An alpha-zero fragment contributes no source RGB to the framebuffer. Do not multiply RGB by alpha in this shader unless you also switch to a premultiplied-alpha blend convention. The surface’s sRGB format encodes the linear blended result for display.

Add this procedure in renderer/texture.odin. vendor:stb/image is the pinned Odin distribution’s native image decoder binding; it introduces no new downloaded library and hides no WebGPU calls. #load(..., []u8) in game.Init embeds the PNG bytes at compile time, so launching from a different working directory still works. Changing a PNG requires rebuilding. This simple asset policy is intentional, not a runtime asset manager.

The decoder takes an address and a C integer byte count. The first checks reject an empty image or a count too large for that integer. It then reads the header and checks positive width and height against the device’s texture-size limit before allocating pixels. Asking for four output channels gives both images the same RGBA byte layout; the RGB room receives alpha 255. channels reports the original file’s channel count. The decoder owns the returned allocation, so stbi.image_free releases it after upload.

The texture descriptor allocates one 2D, single-sample image with one mip level and one layer. RGBA8UnormSrgb stores four 8-bit normalized channels and decodes sRGB color to linear values when sampled; alpha remains linear. TextureBinding permits shader sampling. CopyDst permits the upload. It is not a render attachment and does not need that permission. Its format need not equal the window’s BGRA surface format: sampling produces a shader value, and the pipeline writes that value to the differently formatted attachment.

The destination names the texture receiving the pixels. The row layout says that each pixel occupies four bytes and each row occupies width × 4 bytes. The extent supplies the upload width and height. QueueWriteTexture accepts these tightly packed rows. For the 1254-pixel player, one row has 5016 bytes. The 256-byte row alignment required by buffer-to-texture copy commands does not apply to this queue-write operation.

The call consumes/copies the CPU data for the upload before returning; it does not promise that GPU work has finished. We can free decoded pixels afterward because the implementation owns the queued transfer. Subsequent submissions to this queue observe the earlier texture writes. We do not poll the GPU after each upload.

In renderer/texture.odin: Finish upload_rgba with this block immediately after wgpu.QueueWriteTexture. Keep the allocation and upload blocks above it, then close the procedure with one closing brace. Complete file with surrounding code.

The slot keeps three handles: texture storage, its view, and the bind group connecting that view and sampler to group 1. Only after all three succeed do we increase texture_count and return the nonzero ID. Failed initialization returns zero and takes the application’s shutdown path. Shutdown examines all slots, including a partly created one. We do not retry a failed load or recycle texture slots in this program.

Add Sprite to the renderer API. Between Begin_Frame and End_Frame, it writes four CPU-side vertices and one texture ID into fixed-capacity arrays. Nothing has reached the GPU yet. The room is submitted first and the player second. Their positions are independent because each sprite has its own vertex bytes; repeatedly updating a single transform uniform before one submission would instead make all draws read the final value.

Each sprite needs four vertices and six indices. The renderer reserves space for 256 sprites, so the arrays hold 1024 vertices and 1536 indices. Sprite number 0 uses indices 0,1,2,0,2,3; sprite number 1 uses 4,5,6,4,6,7. The largest possible index is 1023, which fits in u16. The index array is uploaded once because this pattern does not change when pictures move.

A bounded API should fail visibly

Eight texture slots include one internal white pixel, leaving seven for game images. A frame holds 256 sprites, including debug rectangles. Invalid IDs and excess sprites set a flag; End_Frame reports Fatal before uploading. Capacity is a project constraint, not an invitation to silently drop draws. There are no per-frame heap allocations in our sprite recorder.

End_Frame keeps the surface acquisition and cleanup rules from the old renderer. After a successful acquisition, it writes the world size to the view uniform and uploads only the vertices used by this frame. The number of bytes is count × 4 × size_of(Vertex). A skipped acquisition needs no vertex upload.

19.12Fit a room, do not resize the world#

In renderer/renderer.odin: Inside End_Frame, insert this viewport/scissor block after defer wgpu.RenderPassEncoderRelease(pass) and before wgpu.RenderPassEncoderSetPipeline. Keep the pass setup and draw loop. Complete file with surrounding code.

Replace the window-sized game extent with 384 × 256 world units. The renderer queries physical framebuffer dimensions, chooses the smaller axis scale, rounds it down to a whole number when at least one-times scale fits, and centers a viewport. Very small windows use a fractional fit instead of cropping. Clear still initializes the entire attachment, producing dark letterbox bars. The scissor bounds writes to the viewport region; the viewport transforms coordinates, while the scissor rejects output samples outside a rectangle. Both reset with each new render pass, so both are set each frame.

The room occupies the complete world rectangle. The player’s whole transparent canvas occupies 32 × 32 units. Its visible artwork uses only part of that canvas, so {16,30} is an authored anchor near the boots, not half the visible character’s height. We round the displayed feet position, then subtract this anchor. Simulation retains fractional movement. This avoids accumulating rounding error and establishes the foot point we will use for collision.

19.16Experiments#

These short, optional checks help you test the explanation. Predict the result first, then run the program. Restore the chapter’s baseline before continuing; later chapters start from the result taught here, without the optional changes.

  1. Tint the player {1, 0.5, 0.5, 1}; leave the room white. Observe that texture color is multiplied, not replaced.
  2. Draw the player before the opaque room. Explain why it disappears without blaming the upload.
  3. Make the window narrower than 384 physical pixels; compare fractional fitting with the normal integer-scale viewport.

19.20Challenges#

Optional extensions. The complete game in chapter 23 requires none of these. Work in a separate copy if you want to explore; the next chapter starts from the unmodified result described here.

  1. A decoration layer

    Draw an additional tinted or translucent decoration using an existing texture or the renderer’s white rectangle. Choose its place in painter’s order explicitly.

    Check your result: The decoration appears in front of or behind the player as intended and does not upload texture pixels every frame.

  2. An image-size diagnostic

    Display or log source texel dimensions, chosen world size, and current viewport scale for an asset.

    Check your result: You can explain an image’s apparent size without treating its PNG dimensions as game coordinates.
