6.1Why we ask the surface what it supports#

A configured surface is an agreement about future frame images: which device draws them, their dimensions, their color representation, and how they are presented. Configuration does not contain the room artwork, and it does not draw a frame. It prepares the presentation system for the acquisition we add next.

Read BGRA8UnormSrgb in pieces: BGRA is the storage channel order, 8 is bits per channel, Unorm maps unsigned integers to a normalized range, and Srgb describes RGB color encoding. The shader still returns RGBA values. The backend performs the format conversion; manually swapping red and blue would introduce an error.

A usage flag declares what operations an image permits. Our window images need RenderAttachment because a render pass writes them. Their dimensions use physical pixels because they describe actual backing images. The game’s own coordinate units are a separate choice that chapter 13 will make explicit.

6.2A surface is a negotiation point#

The instance created the surface independently of the device. We now join them. Capabilities describe choices supported by this surface and adapter pair: color formats, texture usages, presentation modes, and compositing-alpha modes. Querying the adapter alone is insufficient; the display system and window backend also constrain presentation.

A texture format specifies how texels are represented and interpreted. In BGRA8UnormSrgb, there are four 8-bit channels stored in blue-green-red-alpha order; RGB uses an sRGB transfer function, and normalized numeric values represent channel magnitudes. The fragment shader still returns an RGBA vector. It does not swizzle red and blue to match the storage order; the format tells the backend how to encode its output.

The sRGB part matters even for a flat rectangle. We treat shader colors and clear colors as linear-light values. Rendering to an sRGB attachment encodes RGB for storage; blending is evaluated with the appropriate linear interpretation. Alpha is not sRGB-encoded. We deliberately support only the common RGBA/BGRA sRGB surface formats in this book. If neither is offered, initialization explains the unsupported configuration and stops. A linear fallback would require an explicit color-output policy, not just a different enum.

6.3Read, select, then release the capability lists#

Add gpu_choose_surface to gpu.odin. In gpu_init, call it after gpu_request_device succeeds. The selected values are copied into gpu.config; the native capability arrays are freed before the function returns.

SurfaceGetCapabilities is a small Odin convenience wrapper over a native output-pointer call. It returns a struct and status. Inside the struct, arrays are still native pointer/count pairs. Slicing caps.formats[:caps.formatCount] creates a temporary Odin view over those elements; it does not transfer ownership. SurfaceCapabilitiesFreeMembers is the matching native deallocator. Do not call Odin delete on those pointers or retain the slices after freeing them.

FIFO presents images in submission order with display pacing; it is the baseline supported mode. “Vsync” is a useful shorthand, but neither the return of present nor the return of submit tells us the exact instant a pixel appears on a monitor. Compositors and backend buffering still exist. The code checks for FIFO instead of guessing an unsupported present mode.

Surface composite alpha controls how the window image is combined with the desktop. It is separate from blending a character over its background inside our render pass. We select opaque compositing if listed, otherwise use the implementation’s automatic policy. Our clear alpha is one, so the complete window image remains opaque. .Auto is a valid selection even though capability lists do not enumerate it.

DeviceWhich logical device will render these images

Width and heightActual framebuffer dimensions in physical pixels
Present modeHow completed images are scheduled for presentation
Alpha modeHow the window image participates in desktop compositing

A usage flag is permission for a category of operations. An attachment-only surface texture is not automatically a texture that we may sample, copy from, or use as storage. Declaring intended usage lets validation detect incompatible operations and lets the backend create suitable resources. We ask for exactly the usage that our current program needs.

Add gpu_refresh_surface. The initial call happens in gpu_init. We query GetWindowSizeInPixels, because configuration dimensions describe the image, not necessarily SDL’s logical window units. A zero width or height is not a legal rendering configuration. We skip it and try later. We also reject an extent larger than the device’s maxTextureDimension2D rather than issuing a predictably invalid configure call.

The stored descriptor is application-owned CPU data. SurfaceConfigure consumes its values and manages the presentable images internally. The configured flag records whether this application successfully established a usable configuration; dirty requests reconfiguration even if dimensions are unchanged. We will set dirty when acquisition reports an outdated or suboptimal surface. Calling this helper every frame later does not mean calling SurfaceConfigure every frame: its comparison gates the expensive operation.

Configuration does not draw

The window may still show an undefined-looking client area. We have selected the properties of future frame images, but have not acquired, cleared, or presented one. Surface creation and surface configuration are two separate milestones.

6.5What resizing will and will not invalidate#

A size change replaces the surface’s image configuration. It does not change our color format, vertex format, shader code, or character buffer. Therefore it does not inherently invalidate the render pipeline we will create. A format or sample-count change would affect pipeline compatibility and require matching resources. The surface must not be reconfigured while our application still holds the preceding frame’s acquired texture; the frame procedure’s scoped releases will enforce that boundary.

6.10Challenges#

Optional extensions. The complete game in chapter 23 requires none of these. Work in a separate copy if you want to explore; the next chapter starts from this chapter’s supplied baseline.

  1. Show the negotiation

    Print the advertised surface formats and presentation modes once, marking the selected entries. Do this before freeing the capability arrays.

    Check your result: The selected format and FIFO mode are visibly supported by this surface/adapter pair.

  2. A reconfiguration counter

    Count actual SurfaceConfigure calls separately from calls to the refresh helper. Use the counter again when resizing is enabled in chapter 13.

    Check your result: An unchanged window does not continuously reconfigure, even though the helper is checked each frame.
