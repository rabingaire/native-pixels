6.1Choose the images the window will display#

The device and queue now exist. Before requesting a frame image, we must choose its size, color format, and presentation settings. The supported choices come from the surface and adapter together.

We will read those choices, save a supported configuration, and apply it using the window’s actual pixel dimensions. The new procedures belong in src/gpu.odin. Configuration prepares images for use; the following chapter will put a background color into one.

6.2A surface is a negotiation point#

The instance created the surface independently of the device. We now join them. Capabilities describe choices supported by this surface and adapter pair: color formats, texture usages, presentation modes, and compositing-alpha modes. Querying the adapter alone is insufficient; the display system and window backend also constrain presentation.

An image stores a number for each color channel. A byte contains eight bits and can represent 256 different unsigned values, from 0 to 255. BGRA8UnormSrgb stores one byte each for blue, green, red, and alpha. Unorm maps those stored values to the range 0 to 1. Alpha describes opacity for a chosen composition rule; our window will remain opaque. The shader still writes red, green, blue, and alpha in that order. The format handles their storage order.

sRGB describes how RGB values are encoded for storage and display. Our shader and clear values represent linear light: twice the value means twice the light contribution. The sRGB surface converts those linear RGB values to its storage encoding. Alpha is not sRGB-encoded. We select a supported RGBA or BGRA sRGB format and stop with an error if neither exists, so the program always uses the same color interpretation.

6.3Read arrays, slices, and native lists#

Surface capabilities include a list of formats. Before reading it, distinguish an array, which stores elements, from a slice, which describes a range of existing elements:

[3]int is an array of three integers. []int is a slice of integers. A slice keeps an address and a length; creating one does not copy the elements. len(first_two) is 2. The upper bound in [:2] is excluded. raw_data(first_two) gives the address of the first element when a native call needs it separately from the length.

Native interfaces often return that address and length as two fields. Here caps.formats points to format values and caps.formatCount tells us how many exist. caps.formats[:caps.formatCount] makes a slice so an Odin loop can read them. The native library allocated the list, so its matching free procedure must release it. Neither the pointer nor a slice remains usable after that release.

The refresh procedure also imports core:c. Its c.int type matches the integer fields SDL writes through output pointers. u32 is an unsigned 32-bit integer. A conversion such as u32(width) makes the destination type explicit; first check that width is positive so a negative error value cannot become a large unsigned size.

Some binding helpers return two values. caps, status := wgpu.SurfaceGetCapabilities(...) receives both the data and the result status. _ discards a returned value deliberately. The status must be checked before using data from a call that can fail.

6.4Read, select, then release the capability lists#

Add gpu_choose_surface to gpu.odin. In gpu_init, call it after gpu_request_device succeeds. The selected values are copied into gpu.config; the native capability arrays are freed before the function returns.

In src/gpu.odin: Add the complete gpu_choose_surface procedure at file scope, after the package/import lines and outside every other procedure. Keep the other declarations. Complete file with surrounding code.

SurfaceGetCapabilities is a small Odin convenience wrapper over a native output-pointer call. It returns a struct and status. Inside the struct, arrays are still native pointer/count pairs. Slicing caps.formats[:caps.formatCount] creates a temporary Odin view over those elements; it does not transfer ownership. SurfaceCapabilitiesFreeMembers is the matching native deallocator. Do not call Odin delete on those pointers or retain the slices after freeing them.

FIFO means first in, first out: images are presented in the order submitted, paced by the display system. It is the baseline mode, and our code still checks that the surface advertises it. Returning from a present call does not tell us the exact instant the monitor shows an image; the operating system may still be scheduling it.

Surface composite alpha controls how the window image is combined with the desktop. It is separate from blending a character over its background inside our render pass. We select opaque compositing if listed, otherwise use the implementation’s automatic policy. Our clear alpha is one, so the complete window image remains opaque. .Auto is a valid selection even though capability lists do not enumerate it.

6.5Configuration is a contract for future acquisitions#

DeviceWhich logical device will render these images

Width and heightActual framebuffer dimensions in physical pixels
Present modeHow completed images are scheduled for presentation
Alpha modeHow the window image participates in desktop compositing

A usage flag declares which operations a resource may be used for. RenderAttachment permits drawing into the image as a render-pass output. This is all the surface needs here. If we try an operation that was not permitted when configuring the resource, WebGPU can report a validation error: a message that an API rule was broken.

Add gpu_refresh_surface. The initial call happens in gpu_init. We query GetWindowSizeInPixels, because configuration dimensions describe the image, not necessarily SDL’s logical window units. A zero width or height is not a legal rendering configuration. We skip it and try later. We also reject an extent larger than the device’s maxTextureDimension2D rather than issuing a predictably invalid configure call.

In src/gpu.odin: Add the complete gpu_refresh_surface procedure at file scope, after the package/import lines and outside every other procedure. Keep the other declarations. Complete file with surrounding code.

The stored descriptor is application-owned CPU data. SurfaceConfigure consumes its values and manages the presentable images internally. The configured flag records whether this application successfully established a usable configuration; dirty requests reconfiguration even if dimensions are unchanged. We will set dirty when acquisition reports an outdated or suboptimal surface. Calling this helper every frame later does not mean calling SurfaceConfigure every frame: its comparison gates the expensive operation.

Configuration does not draw

The window may still show an undefined-looking client area. We have selected the properties of future frame images, but have not acquired, cleared, or presented one. Surface creation and surface configuration are two separate milestones.

6.8Experiments#

These short, optional checks help you test the explanation. Predict the result first, then run the program. Restore the chapter’s baseline before continuing; later chapters start from the result taught here, without the optional changes.

  2. Make the initial window much smaller. The configuration dimensions should change; the chosen adapter and format usually should not.

6.12Challenges#

Optional extensions. The complete game in chapter 23 requires none of these. Work in a separate copy if you want to explore; the next chapter starts from the unmodified result described here.

  1. Show the negotiation

    Print the advertised surface formats and presentation modes once, marking the selected entries. Do this before freeing the capability arrays.

    Check your result: The selected format and FIFO mode are visibly supported by this surface/adapter pair.

  2. A reconfiguration counter

    Count actual SurfaceConfigure calls separately from calls to the refresh helper. Use the counter again when resizing is enabled in chapter 13.

    Check your result: An unchanged window does not continuously reconfigure, even though the helper is checked each frame.
