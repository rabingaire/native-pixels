14.1Give the application something to remember#

The renderer receives fixed position and color values. We now want keyboard input to affect those values while the application runs. Game state is the data that remains from one iteration to the next.

Create src/game.odin for that state and its update procedure. First, held movement keys will change the character’s tint. This proves that input reaches the shader before we add the elapsed-time calculation needed for movement.

14.2Put meaning on the CPU side#

A WebGPU buffer contains values a shader needs. It should not be the only record of where the character is. Game state belongs to the CPU simulation, where input and movement rules can update it without depending on WebGPU handles. Rendering receives a snapshot of the values it needs and translates those into the uniform buffer.

Add src/game.odin. Its Game struct contains position, size, and tint. The file also contains a small SDL input adapter and the game update procedure; four directions need only a small input procedure. The state and update parameters remain independent of WebGPU. game_update does not acquire images, create buffers, or know what a bind group is.

In src/game.odin: Add the complete Game struct at file scope, after the package/import lines and outside every other procedure. Keep the other declarations. Complete file with surrounding code.

Initialize game in main after renderer initialization with position (120,100), size (48,64), and white tint. The renderer no longer manufactures these values. Its arguments become position, size, tint, and view_size in addition to its connection and resource owners. The renderer receives only the values it draws.

14.3Held keys are state, not repeated key-down events#

In src/game.odin: Add the complete read_movement procedure at file scope, after the package/import lines and outside every other procedure. Keep the other declarations. Complete file with surrounding code.

Call this after draining SDL events. GetKeyboardState(nil) returns a pointer to SDL’s keyboard-state array, whose lifetime SDL manages. We read it during this iteration and never free or modify it. The scancode enum indexes physical key positions. This is appropriate for movement controls; text entry would use different SDL facilities. W and the up arrow both contribute negative y, because our logical game coordinates increase downward.

The horizontal axis adds one for right and subtracts one for left. Opposite directions cancel. Testing D or the right arrow with a boolean OR means holding both does not double speed. Keyboard auto-repeat is irrelevant: a held key is sampled as down each iteration. A very short press and release both processed before sampling might not be observed as held; discrete actions such as “jump once” often use key-down events instead. Our movement needs continuous held state.

When the window lacks input focus, return zero direction. This prevents the character from continuing under an input state sampled while another window is active. SDL continues to own focus and event handling. We do not poll platform-specific keyboard APIs behind its back.

14.4First prove the path with color#

In src/game.odin: Add the complete game_update procedure at file scope, after the package/import lines and outside every other procedure. Keep the other declarations. Complete file with surrounding code.

This update intentionally does not move anything yet. It sets a visible tint while a nonzero direction is held. A stationary colored rectangle is easier to diagnose than a moving object with a broken time unit. The next chapter removes this temporary tint-only update and replaces it with delta-time movement. Do not carry both updates forward accidentally.

Move the logical window-size query from renderer_frame to main, after event processing. Main now needs that extent to coordinate update and render. Remove core:c from renderer imports and add it to main. The physical framebuffer-size query remains in gpu_refresh_surface because it configures GPU presentation. Nothing changes in the uniform byte layout or bind group.

In src/main.odin: Inside main, insert this block in the running loop after if gpu_failed() { break } and before the renderer_frame call. Replace that render call with the next snippet. Complete file with surrounding code.

Inside renderer_frame, replace fixed uniform position, size, tint, and view extent with those parameters. The camera stays zero. The shader still multiplies vertex color by tint, so the changed CPU game value reaches the fragment output through the existing uniform upload and interpolation path.

14.5Why this loop order works#

Processing events first makes the keyboard sample current and observes shutdown before further work. Updating next establishes the game state for this iteration. Rendering afterward presents that updated state. If render ran before update, the visible image would lag one simulation iteration behind the sampled input. The GPU may still execute asynchronously, but the CPU’s intended data ordering is now straightforward.

A render skip does not inherently mean game state must freeze. This chapter skips update when the logical extent is zero or the window is minimized, because our world is the visible window and there is nothing useful to interact with then. Surface timeouts can skip only presentation. The next chapter will ensure that neither case creates a large accumulated time step when drawing resumes.

14.8Experiments#

These short, optional checks help you test the explanation. Predict the result first, then run the program. Restore the chapter’s baseline before continuing; later chapters start from the result taught here, without the optional changes.

  1. Hold opposite directions. The tint should return to its neutral state because the direction sums to zero.
  2. Hold D and the right arrow together. Verify that the computed x direction is still one.
  3. Temporarily change the tint in main after update. Explain why that value wins for this frame’s render snapshot.

14.12Challenges#

Optional extensions. The complete game in chapter 23 requires none of these. Work in a separate copy if you want to explore; the next chapter starts from the unmodified result described here.

  1. A reset action

    Use a nonrepeated key-down event to request resetting the character to its initial position. Apply the request in game update.

    Check your result: Holding the key does not repeatedly reset future movement, and rendering does not mutate game state.

  2. A selectable appearance

    Add a small palette index to game state and cycle it with a discrete key press. Derive the tint from that index.

    Check your result: The selected appearance remains after release and survives a resize.
