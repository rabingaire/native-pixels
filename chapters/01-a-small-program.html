1.1Start with an empty project#

You will build one application from the first source file to the final animated room. This chapter creates the working directory, introduces the notation in the first program, and installs the tools needed to run it. No Odin or graphics knowledge is assumed.

You need a desktop computer running macOS, Windows, or Linux, a plain-text editor, and a terminal. Commands for installing the native tools are included below. The result of this chapter is a version report in the terminal; the window comes next.

1.2The game we will build#

By the end of this book, you will control an animated character in a furnished room. The character will stop at walls and furniture. You will be able to resize the window and display the rectangles used for collision. We will build this application in small steps, explaining what each new piece makes possible.

Odin runs the application. SDL3 creates the desktop window and reports input. WebGPU lets us draw using the graphics processor. We use wgpu-native, a library that implements WebGPU for desktop applications. A library is code our application calls to perform a task. Its application programming interface, or API, is the set of procedures and types we use to call it. Native means that our finished executable runs directly as a desktop application; this web page only displays the book. You do not need prior experience with these tools or with graphics programming.

We will open a window, then draw a background color into it. We will add a triangle, turn it into a rectangle, and make it move. That rectangle teaches the drawing and movement rules we will reuse for the room artwork. Textures, collision, and animation each solve a limitation of the program we have at that point.

1.3Create one working directory#

Open a terminal: Terminal on macOS/Linux, or PowerShell on Windows. Commands run relative to the terminal’s current directory. Choose a place for your work, then run these commands one line at a time. mkdir creates a directory; cd enters it.

Use a plain-text editor to create main.odin inside src. Check that the editor has not added a hidden .txt extension. All paths in the lessons are relative to native-pixels-game. Source files belong in src for now; compiled executables go in build. Keep using this same project as the chapters continue.

All file paths are relative to native-pixels-game. A code block caption names the file and the part being discussed. Instructions above a focused excerpt say whether to add, replace, or read the code, name its enclosing procedure when needed, and identify the surrounding statements. Keep code outside the named replacement. A complete procedure replaces the existing procedure, including its body; do not append a second copy. Small syntax examples are marked as examples and do not become extra project files. The “Complete file with surrounding code” links lead to the full listing for this chapter, including its package line and imports. 1.4Read a small Odin program#

A program is a set of instructions saved as text. Odin is the language we will use to write those instructions. A compiler translates the text into an executable: a file your operating system can run. Before adding any window code, read this small example. It is a syntax example, not an extra file to keep in the game.

A package groups the Odin files in one directory. The first line names this package character. An import makes another package available; core:fmt supplies text-formatting procedures. A procedure is a named group of instructions. Odin starts this program by calling the procedure named main.

In main :: proc(), :: declares a name whose value will not be reassigned, and proc() defines a procedure with no inputs. Its instructions go between braces. fmt.println(...) calls a procedure from the imported package. The text between quotation marks is a string. Parentheses contain the input to the call; println writes it to the terminal and ends the line.

The CPU, or central processing unit, runs these instructions. Later we will also write small programs for the GPU, or graphics processing unit, to calculate where shapes appear and what colors they have. For now, all our program does is print text.

1.5Check the libraries before opening a window#

The first project file will print library versions instead of a greeting. This checks the installation before we add window or drawing code. A binding tells Odin which procedures a native library provides and how to call them. The matching library supplies their implementation. The compiler checks our Odin code, the linker connects its calls to libraries, and the operating system loads the executable and any shared libraries when it runs.

The two vendor imports below provide the SDL and WebGPU bindings. The names sdl and wgpu are local names used before a dot, just as fmt is. GetVersion() is a call with no inputs. Its returned number becomes an input to the printing call. wgpu.BINDINGS_VERSION_STRING is a named value containing the binding’s expected version.

1.6Install the matching tools#

Install Odin dev-2026-09:a2fb372b7, wgpu-native 29.0.1.1, and SDL 3.4.16. The following instructions include the downloads, library locations, and build commands. Read the common Odin and wgpu-native steps, then follow the SDL subsection for your operating system. You do not need to carry out the other platforms’ steps.

These versions are a matched set for this edition. Native library calls depend on exact argument types and data layouts, so replacing only the WebGPU binary with a different version can break them. Internet access is needed to obtain these tools. Once they are installed and you have saved the book’s artwork, the project can be built offline.

1.7Choose the version for your computer#

Use Odin dev-2026-09 with its bundled vendor packages, wgpu-native v29.0.1.1, and SDL 3.4.16. The Odin SDL declarations identify version 3.4.2; the runtime baseline is the later compatible 3.4.16 bugfix release. Do not combine a different native WebGPU binary with these descriptor declarations. Use a dedicated writable Odin installation for this book so adding libraries does not modify another project’s toolchain.

1.81. Install the matching Odin release#

Download the appropriate official Odin release archive from the table below. Extract it to a writable tools directory, keeping its core, base, and vendor directories beside the compiler. PATH is the list of directories your terminal searches for commands. On macOS/Linux, run export PATH="/absolute/path/to/odin-folder:$PATH", replacing the example directory with the folder containing the compiler. In Windows PowerShell use $env:Path = "C:\tools\odin;" + $env:Path with your actual compiler folder. These changes apply to the current terminal; repeat them in a new terminal. Keep tool directories free of spaces for the linker commands below. Run odin version and odin root to confirm which installation you are using. The tested compiler reports dev-2026-09:a2fb372b7.

macOS needs the Apple command-line developer tools/SDK and a Metal-capable Mac. Windows needs Visual Studio Build Tools with the Desktop development with C++ workload and a Windows SDK, even though application code is Odin: these supply the system linker and libraries. Linux needs a compatible system linker/libc and graphics drivers; use the binary archive for the machine architecture. On macOS, run xcode-select --install in Terminal and finish the installer. On Windows, install the named C++ workload through the Visual Studio Installer, then open Developer PowerShell for Visual Studio with the x64 tools. If your installer provides an x64 Native Tools Command Prompt instead, enter powershell there before using this book’s PowerShell commands. Return to your native-pixels-game directory with cd and its full path. The Linux packages appear in the Linux subsection below.

1.92. Put wgpu-native where the binding looks#

Download the matching wgpu-native release archive. Inside the Odin root, the binding expects a directory named after the archive without .zip, then an inner lib directory. Extract into that named directory; do not accidentally insert a second identical directory level. Run the commands from native-pixels-game. BOOK_ODIN_ROOT stores the compiler installation path returned by odin root. Shell variables hold text we reuse in later commands; this one tells the extraction command where to put the native library.

A hash is a calculated fingerprint of a file. Run the download and hash commands first, compare the printed value with the table at the end of this installation section, and only then run the extraction commands. A matching SHA-256 value confirms that you have the listed archive. For Intel macOS substitute wgpu-macos-x86_64-release in both places. Linux uses wgpu-linux-x86_64-release or wgpu-linux-aarch64-release and sha256sum wgpu.zip. The exact extracted static library path is shown below. The default binding links a static release build of wgpu-native. -debug for Odin does not switch the native library to a debug archive; that separate switch is -define:WGPU_DEBUG=true and is not used here.

A static library is linked into the executable. The wgpu-native archive used here is static, so you do not copy a separate WebGPU library beside your application. Odin’s binding already names the required system libraries. SDL uses a shared library in this setup: the operating system must be able to find that separate file when the executable runs.

1.103a. SDL on macOS#

The locally verified runtime was Homebrew SDL3 3.4.16. brew install sdl3 is convenient only while it resolves to that version; it is not a permanent version pin. For a versioned installation, download the SDL3 3.4.16 source archive, verify its hash, and build a shared library into a writable prefix. Install CMake from its official macOS installer. In Terminal run export PATH="/Applications/CMake.app/Contents/bin:$PATH" if you installed it in Applications, then check cmake --version. The Apple command-line tools supply the build tool. CMake builds SDL; you will use Odin to build the game.

From your native-pixels-game directory, build with the absolute install prefix retained in BOOK_SDL_PREFIX. The -L option tells the linker where to find SDL while building. The rpath option records where the executable can find that shared library when it runs. Paths embedded in the linker flag string below are assumed not to contain spaces; use a simple tools prefix for reproducibility. For Homebrew Apple Silicon use /opt/homebrew/lib; for Intel Homebrew normally /usr/local/lib.

Terminal launching is sufficient; no Xcode project or app bundle is required to follow the book. Keep using the terminal build and launch commands throughout the book.

1.113b. SDL on Linux#

Install a C/C++ toolchain, CMake, Ninja or Make, pkg-config, and SDL’s window-backend development dependencies before building the pinned SDL source. On Ubuntu 24.04-style systems, a focused desktop starting set is below. Package names vary by distribution. SDL’s Linux build dependency guide lists broader backend options. You also need a working Vulkan loader and a driver for your GPU; an installed loader alone is not a GPU driver.

Download and extract the same SDL source archive as macOS, checking it with sha256sum. Run the CMake configure/build/install commands above with a Linux BOOK_SDL_PREFIX. Inspect CMake’s summary and confirm that X11 and/or Wayland video support was enabled. Optional audio-device warnings do not require adding audio to this application, but missing both desktop window backends is a blocker.

Run inside an actual desktop session with permission to access its display and GPU. A dummy SDL video driver cannot supply a presentable X11/Wayland surface. A Vulkan adapter failure should be investigated with the installed graphics driver and surface backend before changing shader code. These Linux instructions and branches have not been executed on a Linux machine during this edition’s verification.

1.123c. SDL on Windows x64#

Download the SDL3 3.4.16 Visual C++ development archive, not the MinGW archive. The pinned vendor:sdl3 Windows import names SDL3.lib relative to that package. Copy the matching x64 import library into the dedicated Odin installation’s vendor/sdl3 directory and put its matching DLL beside the executable. This intentionally replaces that dedicated installation’s bundled SDL library pair with the pinned runtime pair.

Use the x64 compiler, SDL library, and wgpu-native MSVC archive together. Keep the SDK system libraries available to Odin’s linker. A missing SDL3.dll is a runtime dependency problem; a missing symbol during linking usually means a mismatched import library. No SDL2main or hand-written C entry point is required for this Odin main procedure. Windows source is supplied but was not executed here.

1.14Run the first result#

The build command in your platform’s instructions reads src and writes the executable into build. Run that executable from the same terminal. It prints four lines and exits; no window should appear yet. The version procedures do not initialize a GPU, so a successful run proves installation and linkage, not graphics support.

Keep the exact build command that worked for your platform. Use it after saving changes in each chapter, and then run the executable again. -debug includes debugging information; -vet enables extra compiler checks. If you open a new terminal, restore any PATH or SDL-prefix setting used by that command.

For reference, SDL packs its version as major × 1,000,000 + minor × 1,000 + patch. WebGPU packs four components into four bytes: hexadecimal 1d is decimal 29, so 1d/00/01/01 represents 29.0.1.1. These formats explain why the two libraries print different-looking numbers.
