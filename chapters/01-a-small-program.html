1.1Before you type the first program#

You need basic programming experience: variables, functions, conditionals, loops, and structs. You do not need graphics experience. The CPU runs our Odin application; the GPU runs the small WGSL programs that decide where geometry goes and how it is colored. SDL connects the application to the operating system. We introduce each graphics object when the next visible result needs it.

There are three steps between source and a running window. The compiler checks Odin and produces machine code. The linker connects that code to native libraries. The operating system then loads the executable and its required shared libraries. A binding is a set of declarations telling Odin how to call a library; it does not replace the library. The version probe separates installation failures from the rendering problems we will meet later.

Choose a working method now. You can edit a copy of the preceding checkpoint, or read and run the supplied completed checkpoint. A checkpoint is a full project directory, not just main.odin: keep relative folders together. Excerpts show the relevant change; the expandable complete files are the reference when placement is unclear. The optional experiments and challenges never supply code required by the next chapter.

1.2The destination#

We will build a desktop application in Odin. SDL creates a window and tells us what the user is doing. WebGPU turns a few vertices into a colored character. Holding D moves that character to the right at a speed measured in window units per second. Resizing the window preserves the character’s proportions. This modest result is useful precisely because the graphics machinery remains visible: we can follow a position all the way from an Odin struct to a displayed image.

There is no engine to learn alongside the GPU. Our foundation renderer owns a pipeline, three small buffers, and a bind group. Each frame it acquires an image, records a render pass, submits the work, and presents. A pair of eyes and a mouth will eventually come from a tiny fragment-shader calculation. No image loader, sprite atlas, physics system, or asset database is required for the first 18 chapters. Part V then extends this foundation with a furnished pixel-art room, a renderer API, authored collision, and directional animation. It introduces textures only after the geometric moving character is understood.

The website you are reading is static HTML. The program it teaches is a native executable; it never runs in this page. All host application files are Odin, and all shader files are WGSL. The site’s small JavaScript file only enhances reading, copying code, and exploring diagrams. You can read the entire book with JavaScript disabled.

WebGPU bindingvendor:wgpu from the same Odin releaseOdin declarations for the native ABI
Implementationwgpu-native v29.0.1.1Validation, resource management, WGSL compilation, backend submission
Shader languageWGSL as accepted by that wgpu-native releaseVertex placement and fragment color

Odin’s vendor package documentation names wgpu-native 29.0.1.1 explicitly. We choose that pair rather than independently upgrading the binding and binary. Native WebGPU is a C ABI: enum values, descriptor fields, callback signatures, and exported symbols must agree. A newer binary is not automatically interchangeable. The Odin spelling AllowSpontaneos, including its missing “u,” is real in this release; we will use it exactly.

Dawn is another maintained implementation of native WebGPU, but the bundled Odin binding is already paired with wgpu-native. Using Dawn here would introduce another ABI integration task with no benefit to the moving rectangle. The implementation underneath wgpu-native is largely Rust; that does not require Rust application code. Odin calls the exported native functions directly.

A dated contract, not a moving target

API verification for this edition is dated 13 September 2026. Follow the platform build appendix before compiling. It pins the native archive names and explains where the Odin package expects them. Later package-manager versions are not the reproducible baseline.

1.4The program takes a small first step#

Add src/main.odin with the following complete file. From the book root, its finished snapshot is checkpoints/01/src. This intentionally links both dependencies before introducing a window: a missing library should be diagnosed as a build problem, without a graphics pipeline muddying the evidence.

sdl.GetVersion() reports the runtime we actually linked, not just the binding’s declared version. SDL encodes major × 1,000,000 + minor × 1,000 + patch, so 3.4.16 prints 3004016. wgpu.GetVersion() packs four version components into bytes; our baseline prints 0x1d000101. Neither call initializes a GPU. The process simply proves that the native symbols can be resolved.

On Homebrew macOS, append -extra-linker-flags:"-L/opt/homebrew/lib" if the linker cannot find SDL3; Intel Homebrew normally uses /usr/local/lib. The appendix explains runtime library lookup separately. A successful compile is not evidence that the GPU supports the program, only that the compiler and linker accepted it.

1.5How the source grows#

Each chapter names the exact file and procedure being added or changed. Focused excerpts teach one decision at a time. The end of every chapter includes the complete source snapshot and an exact change record against the previous chapter. You can build each checkpoint independently, or carry edits forward in your own directory. Concept chapters explicitly keep the preceding program; they never leave half-written code to repair later.

We begin with main.odin. Platform-specific surface creation gets platform.odin because its conditional branches would obscure the portable initialization. gpu.odin owns the connection and presentation configuration. Once drawing exists, renderer.odin owns drawing resources. game.odin arrives when input and position become actual game state. Files share one Odin package; they are not layers of public frameworks.

1.10Challenges#

Optional extensions. The complete game in chapter 23 requires none of these. Work in a separate copy if you want to explore; the next chapter starts from this chapter’s supplied baseline.

  1. A useful dependency report

    Extend the probe to print a readable heading, decoded library versions, and whether they match this edition’s expected values. Keep the expected values together so the report is easy to update.

    Check your result: A deliberately changed expected version produces a clear mismatch message before any window is created.

  2. A portable launch note

    Write a short setup note for a friend using your operating system: source folder, compiler command, executable location, and native library location. Explain which failure is a compile, link, or load failure.

    Check your result: Following the note from a fresh terminal runs the probe without relying on your current working directory.
