13.1Keep the character’s shape while resizing#

The rectangle now uses a shader transform, but its size is based on the framebuffer’s pixel dimensions. High-density screens and resizable windows require us to distinguish that image size from the window’s logical size.

We will enable resizing, pass the logical size to the transform, and keep physical pixel dimensions in surface configuration. The renderer must also skip drawing while the window has no usable extent and resume when it does.

13.2Two sizes are both correct#

On a high-density display, a 960 × 640 SDL window can have a drawable image of 1920 × 1280 pixels. The logical size describes the desktop window’s coordinate extent. The physical size describes the image we render. Feeding 960 × 640 into the surface configuration would allocate or request the wrong drawable extent. Feeding 1920 × 1280 into a projection meant for logical game units would make a 48-unit character appear half as wide relative to the window.

We now define one game unit as one SDL logical window unit. The upper-left remains (0,0), and positive y remains downward. The camera and character position use those units. WebGPU surface dimensions remain physical pixels. The vertex shader maps logical positions to NDC using the logical view extent; the viewport then maps NDC into the full physical attachment.

A 48-unit character in a 960-unit-wide window spans 48/960 of the window width. With a 1920-pixel attachment that is 96 physical pixels; with a 960-pixel attachment it is 48. In both cases its fraction of the logical window is identical. A logical square stays square under the ordinary uniform display scale. We do not need to multiply character coordinates by a scale factor and then accidentally apply that scale twice.

13.3Enable resizing and use the right extent#

In main, replace the initial empty window flags with {.RESIZABLE, .HIGH_PIXEL_DENSITY}; preserve the macOS Metal flag addition. Handle .WINDOW_PIXEL_SIZE_CHANGED and .WINDOW_RESTORED by setting gpu.dirty = true. These events request a refresh. The actual dimensions still come from SDL when preparing the next frame, which naturally coalesces several resize events.

In gpu_refresh_surface, add an early return for a minimized window before querying drawable dimensions. We already skip zero or over-limit dimensions and already reconfigure only on a changed extent or dirty flag. Add the logical size query in renderer_frame and use it in the uniform. This query will move to main when main begins coordinating game updates in chapter 14.

In src/renderer.odin: Inside renderer_frame, replace the uniforms declaration and its QueueWriteBuffer call with this block, after the gpu_refresh_surface guard and before frame := wgpu.SurfaceGetCurrentTexture. Complete file with surrounding code.

The import core:c supplies c.int for SDL’s output pointers. SDL writes C integer dimensions into those locals. Converting them to f32 happens only after checking for a positive extent. That check prevents division by zero in the shader as well as a nonsensical game view.

13.4A resize has an ownership boundary#

No prior acquired texture or view survives a completed renderer_frame call. The next call refreshes the configuration first and acquires afterward. Reconfiguration replaces the presentation images internally; it does not mean destroying and recreating the SDL window or the WebGPU device. We preserve the format, so the existing pipeline remains compatible.

The shader’s new view extent is written every rendered frame. Resizing therefore changes both the backing image extent and the projection’s logical denominator when needed. If only the display scale changes, the physical extent may change while the logical extent remains the same; that is still handled because the surface refresh queries physical pixels independently.

Minimized or zero-sized windows suspend rendering. SDL events and WebGPU completion processing continue in the outer loop, and a short sleep prevents spinning. We do not call SurfaceConfigure with zero dimensions, do not acquire from an unusable extent, and do not pretend the last valid image size is the current game view. Restoration triggers or naturally detects a usable extent and resumes drawing.

13.5Viewport and scissor have separate jobs#

The implicit viewport covers the render attachment, and the default scissor permits the full attachment. To render into a smaller viewport you would explicitly call RenderPassEncoderSetViewport after beginning the pass. That rescales and relocates NDC. RenderPassEncoderSetScissorRect instead restricts framebuffer writes without changing the transformation. Both use physical framebuffer coordinates; neither changes the surface’s allocation.

The scissor will clip the character where it crosses the midpoint, while its apparent size remains the same. The load-operation clear is an attachment operation and is not limited by this later draw scissor. Restore the full scissor or remove the experiment before continuing. We do not add permanent viewport/scissor calls merely to restate the defaults.

13.12Challenges#

Optional extensions. The complete game in chapter 23 requires none of these. Work in a separate copy if you want to explore; the next chapter starts from the unmodified result described here.

  1. An aspect-preserving preview

    Choose a fixed logical canvas and fit it into the window using the smaller axis scale. Center the viewport and leave the cleared attachment visible around it.

    Check your result: A logical square stays square in both tall and wide windows.

  2. Two views of one scene

    Render the character into two non-overlapping viewports using the appropriate view extent for each. Use scissors if geometry must stay inside each panel.

    Check your result: The panels show consistent character proportions and the attachment clear still covers the entire window.
