5.1Choose capability before creating resources#

An adapter represents a candidate GPU and its capabilities. A device is the logical connection created from that candidate; buffers and pipelines belong to that device. The queue accepts ordered uploads and command submissions for it. A laptop with several GPUs makes the distinction obvious, but all three roles still exist on a machine with only one GPU.

A callback is a procedure the library calls to deliver a result. Passing a result pointer through user data lets it write into state our requesting code can inspect. That state must remain valid until completion, not merely until the request function returns. The pinned implementation completes these requests inline; the chapter isolates that assumption so another implementation cannot silently borrow a dead local variable.

A capability is available functionality; a limit is a numeric bound, such as the largest supported texture dimension. Ask for what this game needs. Requesting every optional feature can reject otherwise suitable hardware without making a single rectangle look better.

5.2Three names for three different decisions#

An adapter represents a candidate graphics implementation with particular capabilities. It often corresponds to a physical GPU, but may instead be a software implementation. A laptop can offer more than one adapter. A surface-compatible adapter must be able to present to our chosen window, so we create the surface first and include it in the adapter request.

A device is a logical connection created from an adapter. It owns our buffers, pipelines, and command encoders. The adapter describes what is available; the device establishes what this application is allowed to use. Requesting features and limits is a contract, not a way to manufacture hardware support. Our rectangle needs only baseline functionality, so the device descriptor leaves required features empty and required limits absent.

The queue belongs to the device and accepts ordered work and data writes. It is a CPU-visible handle to an execution abstraction over the GPU backend. We obtain it once with DeviceGetQueue and hold our returned reference until shutdown. Do not create a queue every frame; the ordered stream is exactly what lets this frame’s buffer write precede this frame’s draw.

5.3A request has a result callback#

Add the adapter, device, queue, and completion fields to GPU. Add the request and diagnostic procedures to gpu.odin. Replace the last return true in gpu_init with return gpu_request_device(gpu). This helper is not mysterious setup: its entire implementation is below, and we will account for every descriptor.

Descriptor fieldWhat we are asking for
compatibleSurfaceAn adapter whose backend can present to this surface
powerPreferenceA preference for performance; not a guarantee of a discrete GPU
featureLevel = .CoreThe core WebGPU feature level
defaultQueue.labelA diagnostic name for the device’s queue
Required features / limits omittedThe native implementation’s baseline device contract
Callback infoFunction pointer, delivery policy, and caller-owned result storage

A future is a token representing an operation that can complete asynchronously. In a general native implementation, the function returning does not prove that the callback has run. Callback modes distinguish delivery through waiting, event processing, or spontaneous invocation. Browser WebGPU presents related requests as promises rather than these native callback-info structs.

The exact native implementation matters

The pinned wgpu-native source invokes both request callbacks inside their request functions and returns a null future. It does not implement these requests as delayed work. This edition deliberately uses that verified behavior and asserts that each callback completed. .AllowSpontaneos is the Odin binding’s exact spelling. Do not copy this synchronous result pattern to Dawn, a browser, or an unverified wgpu-native upgrade.

For an implementation with deferred completion, keep result storage alive until the callback completes, pump the documented event/wait mechanism, and coordinate cross-thread delivery with atomics or a mutex. Returning a pointer to a temporary local “result” and then waiting elsewhere is a dangling-pointer bug. Our GPU lives in main, and the version-specific inline calls complete before we inspect its result fields.

5.4Odin meets the callback ABI#

proc "c" matches the native calling convention. Native code does not provide Odin’s implicit context, so the callback establishes runtime.default_context() before using formatting facilities. The userdata1 pointer is the exact gpu pointer we supplied; it gives the callback somewhere to store the owned returned handle. The callback’s message is borrowed text. We print it during the callback instead of retaining a pointer to memory the implementation may immediately free.

The device callback is structurally similar, except that it receives a device handle and stores device_done. A failed adapter request can mean missing drivers, no compatible backend, or a surface that the available adapter cannot present to. A failed device request can mean unsupported requirements or a failure to establish the backend device. Both log the native status and message before initialization returns false.

Install uncaptured-error and device-loss callbacks in the device descriptor before any resources are created. Validation errors are often reported through a callback, not merely as a null handle. Our callbacks report the message and atomically set a process-lifetime gpu_fault flag. Diagnostic delivery may occur on another thread; unlike the pinned inline request-result fields, this flag cannot safely use ordinary unsynchronized access. Process-lifetime storage also avoids a callback holding a pointer into a destroyed renderer.

At the top of each iteration after SDL event processing, call InstanceProcessEvents, then check gpu_failed(). This services native completion work; it is not a command submission and does not wait for every GPU operation. On device loss we stop, release our objects, and let the user restart. Rebuilding every device-dependent resource is outside this small project’s scope, but detecting and explaining loss is not optional.

5.5We own references, not raw hardware#

Add release calls for queue, device, and adapter to gpu_destroy. It first calls the native extension DevicePoll(device, true, nil) to drain outstanding work at shutdown. There is no such blocking call in the normal frame loop. Release decrements the application’s reference; it does not necessarily destroy an underlying allocation at that instant. Related objects and in-flight work can retain what they need.

5.10Challenges#

Optional extensions. The complete game in chapter 23 requires none of these. Work in a separate copy if you want to explore; the next chapter starts from this chapter’s supplied baseline.

  1. A readable GPU report

    Print a small startup report with the adapter information and selected device limits available through the pinned binding. Release any native strings or result members using their matching API.

    Check your result: The report appears once and helps identify which GPU is used on a multi-GPU machine.

  2. An explicit requirement

    Choose a hypothetical maximum sprite-image dimension and compare it with the device limit before loading assets. Explain the requirement in the error message.

    Check your result: A deliberately excessive requirement is rejected clearly without attempting an invalid allocation.
