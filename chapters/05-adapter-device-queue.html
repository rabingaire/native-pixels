5.1Choose a GPU that can use our window#

We have an instance and a surface, but no device for creating drawing resources. We will ask for an adapter compatible with the surface, create a device from it, and obtain the queue that accepts its work.

This request introduces callbacks: procedures the library calls with a result. We will learn that mechanism in a small example before using it for native requests and error reporting. Keep the existing platform file; this chapter extends src/gpu.odin and the main loop.

5.2Three names for three different decisions#

An adapter represents a candidate graphics implementation with particular capabilities. It often corresponds to a physical GPU, but may instead be a software implementation. A laptop can offer more than one adapter. A surface-compatible adapter must be able to present to our chosen window, so we create the surface first and include it in the adapter request.

A device is a logical connection created from an adapter. It owns our buffers, pipelines, and command encoders. The adapter describes what is available; the device establishes what this application is allowed to use. Requesting features and limits is a contract, not a way to manufacture hardware support. Our rectangle needs only baseline functionality, so the device descriptor leaves required features empty and required limits absent.

The queue accepts data uploads and drawing work for the device. It keeps that work in order. We obtain it once with DeviceGetQueue and hold our returned reference until shutdown. Do not create a queue every frame; the ordered stream is exactly what lets this frame’s buffer write precede this frame’s draw.

5.3Let a library call one of our procedures#

So far our code has called SDL and read a return value. The adapter request uses a different form: we give WebGPU a procedure to call with its result. That procedure is a callback. The complete example below demonstrates the idea without graphics types. Read it on its own; do not paste it into your game or replace your existing main. The WebGPU changes follow after this explanation.

The report and calculate procedures are outside main, after the import. The call calculate(report) is the only statement between main’s braces. Execution starts at that call, enters calculate, and then done(7) calls report(7), which prints Result: 7.

The call passes report without parentheses: it passes the procedure itself. calculate calls that procedure with 7. WebGPU also passes a status and a handle to our callback. We supply a pointer to our GPU struct as user data, so the callback knows where to store the handle.

A callback may run before the requesting call returns, or later. That timing determines how long its user data must stay valid. The pinned wgpu-native adapter and device requests call their callbacks before returning. Our request code checks that this happened. This is a property of the selected library version, not a rule for callbacks in general.

The native library calls procedures using C’s calling convention: the rules for passing arguments and results at the machine-code boundary. We write proc "c" to match it. A rawptr carries an address without an Odin pointee type. cast(^GPU)userdata1 restores the type we originally passed. This cast is valid because we supplied a pointer to that same GPU value.

Odin normally supplies a hidden context value to procedures for services such as memory allocation. A C caller does not supply it. Each native callback sets context = runtime.default_context() before using the formatting package.

Error callbacks need one more precaution. A thread is a sequence of CPU work that may run alongside another thread. The native library may report an error from another thread while our main loop reads the error flag. An atomic load or store accesses that shared flag with defined coordination between threads. Both reads and writes use atomic operations; the flag lives for the whole process so a late callback cannot access an expired local variable.

5.5Odin meets the callback ABI#

In src/gpu.odin: Add the complete adapter_ready procedure at file scope, after the package/import lines and outside every other procedure. Keep the other declarations. Complete file with surrounding code.

proc "c" matches the native calling convention. The callback sets runtime.default_context() before printing, as described in the callback example. The userdata1 pointer is the exact gpu pointer we supplied; it gives the callback somewhere to store the owned returned handle. The callback’s message is borrowed text. We print it during the callback instead of retaining a pointer to memory the implementation may immediately free.

The device callback is structurally similar, except that it receives a device handle and stores device_done. A failed adapter request can mean missing drivers, no compatible backend, or a surface that the available adapter cannot present to. A failed device request can mean unsupported requirements or a failure to establish the backend device. Both log the native status and message before initialization returns false.

In src/gpu.odin: Add the complete uncaptured_error procedure at file scope, after the package/import lines and outside every other procedure. Keep the other declarations. Complete file with surrounding code.

Install uncaptured-error and device-loss callbacks in the device descriptor before any resources are created. Validation errors are often reported through a callback, not merely as a null handle. Our callbacks report the message and atomically set a process-lifetime gpu_fault flag. Diagnostic delivery may occur on another thread; unlike the pinned inline request-result fields, this flag cannot safely use ordinary unsynchronized access. Process-lifetime storage also avoids a callback holding a pointer into a destroyed renderer.

At the top of each iteration after SDL event processing, call InstanceProcessEvents, then check gpu_failed(). This services native completion work; it is not a command submission and does not wait for every GPU operation. On device loss we stop, release our objects, and let the user restart. Rebuilding every device-dependent resource is outside this small project’s scope, but detecting and explaining loss is not optional.

5.6Request the adapter, then the device#

Add gpu_request_device to src/gpu.odin. In gpu_init, replace the final return true with return gpu_request_device(gpu). The adapter request includes our surface. After its callback succeeds, the device request installs error reporting and requests a queue. No optional features or larger-than-default limits are required.

In src/gpu.odin: Add the complete gpu_request_device procedure at file scope, after the package/import lines and outside every other procedure. Keep the other declarations. Complete file with surrounding code.

Read the helper from top to bottom. First it asks for a compatible adapter and checks that adapter_ready ran. Then it creates the device descriptor and asks the adapter for a device. Finally it obtains the queue and returns true only if the queue exists and no error callback has set the fault flag. A failure returns through the cleanup already registered in main.

5.7We own references, not raw hardware#

Add release calls for queue, device, and adapter to gpu_destroy. It first calls the native extension DevicePoll(device, true, nil) to drain outstanding work at shutdown. There is no such blocking call in the normal frame loop. Release decrements the application’s reference; it does not necessarily destroy an underlying allocation at that instant. Related objects and in-flight work can retain what they need.

5.14Challenges#

Optional extensions. The complete game in chapter 23 requires none of these. Work in a separate copy if you want to explore; the next chapter starts from the unmodified result described here.

  1. A readable GPU report

    Print a small startup report with the adapter information and selected device limits available through the pinned binding. Release any native strings or result members using their matching API.

    Check your result: The report appears once and helps identify which GPU is used on a multi-GPU machine.

  2. An explicit requirement

    Choose a hypothetical maximum sprite-image dimension and compare it with the device limit before loading assets. Explain the requirement in the error message.

    Check your result: A deliberately excessive requirement is rejected clearly without attempting an invalid allocation.
