18.1Read the program in two directions#

Follow startup forward to understand dependencies: window, surface, compatible adapter, device, presentation configuration, drawing resources. Follow cleanup backward to understand ownership. Then follow a single changing value—position—from input through the CPU update, uniform upload, vertex transform, and resulting coverage.

If position becomes (124,100) on the CPU but the uniform still contains (120,100), the renderer is displaying the old position correctly. Rebuilding a pipeline cannot fix the missing data copy. The purpose of this full walkthrough is to make every visible symptom traceable to a specific boundary.

Checkpoint 18 is a finished geometric demo and a useful debugging reference. It is not the repository’s final application: chapters 19–23 add textures, room composition, collision, diagnostics, and animation. Continue with the baseline here; no optional challenge implementation is assumed in that migration.

18.2The foundation main is the map#

There are no new code changes. Checkpoint 18 is identical to checkpoint 17. Its complete files appear below. The complete-source appendix and project/ contain checkpoint 23, the later animated room; use this chapter’s own listing to follow the foundation walkthrough. Start at main, then follow a single key press through the CPU and GPU. Every helper now names machinery we have already implemented and examined.

The startup order follows dependencies. SDL must exist before its window. The instance must exist before the surface. The surface participates in compatible-adapter selection. The adapter creates a device, and the device supplies a queue. The adapter/surface capabilities and device limits determine configuration. The renderer then creates stable geometry, a shader module, uniform storage, resource layouts, a bind group, and a compatible pipeline. Game state can be initialized independently, but it has no visible effect until a frame uploads it.

18.3Startup creates capabilities, not frames#

The instance is our native implementation context; it is not the hardware. The adapter represents a compatible candidate; the device is the logical resource-owning connection created from it. The queue orders writes and submissions. The surface wraps the native presentation destination. Its configuration defines the images we can acquire, including a format the pipeline must match.

The renderer’s descriptors form two connected contracts. The vertex contract maps the 24-byte Odin record to Float32x2/Float32x4 attributes at locations zero and one. The resource contract maps group zero, binding zero to a 48-byte uniform range. A pipeline layout describes that group interface; the bind group attaches actual storage. The pipeline selects WGSL entry points and fixes triangle topology, blending, sample count, and color target format. None of those objects encodes this frame’s position.

18.4Trace one press of D#

The operating system delivers keyboard information to SDL. Main drains SDL’s queued events, updating SDL’s keyboard state. If the window has focus, read_movement sees D down and returns (1,0), unless the opposite direction cancels it. Main measures dt in seconds. game_update normalizes the direction, multiplies by speed and dt, adds the displacement to game.position, and clamps the result to the logical window bounds.

At an ordinary 60 Hz iteration with no clamp, position (120,100) becomes approximately (124,100). Main passes that value to renderer_frame. It is copied into Uniforms.position, and QueueWriteBuffer schedules the 48 bytes for the GPU buffer. The bind group still names the same buffer. The pipeline has not changed, the index buffer has not changed, and the unit-square vertices have not changed.

During execution, the vertex shader fetches a local corner, such as (1,0), and computes (124,100) + (1,0) × (48,64) − (0,0) = (172,100). With a logical view width of 960, its NDC x is 2 × 172/960 − 1, approximately −0.641667. The top-left corner similarly moved from x=120 to x=124. All corners receive the same world translation, so the rectangle moves without changing shape.

Clipping and the viewport convert those clip coordinates into covered framebuffer samples. The rasterizer interpolates color and local position across the triangles. The fragment shader chooses face or body colors. The blend state combines those colors with the background already cleared into the image. Presentation schedules that image for display. The image contains new pixels; no old character bitmap was physically relocated.

18.5One complete frame, in exact order#

StepApplication operationConsequence
1Poll SDL eventsObserve close, resize, and current keyboard state
2Measure dt; process WebGPU callbacksAdvance clock and observe native failures
3Query logical extent; read input; update gameProduce the CPU state to show
4Refresh physical surface configuration if necessaryPrepare a valid image extent before acquiring
5Write uniformsOrder the new position before the draw submission
6Acquire current surface textureObtain the presentable image for this frame
7Create its texture viewDescribe the color attachment access
8Create command encoder and begin render passRecord a pass that clears its attachment
9Set pipeline, bind group, vertex buffer, index bufferSupply compatible executable state and resources
10DrawIndexed(6,1,0,0,0)Record two triangles for one instance
11End pass and finish encoderProduce a closed command buffer
12Submit to queueHand ordered work to the implementation
13Present surfaceHand the completed-image dependency to presentation
14Release frame-local referencesEnd application ownership without forcing a GPU wait

Uniform upload appears before acquisition in our implementation. It could occur after successful acquisition as long as it is ordered before submission. A timed-out acquisition can therefore leave a harmless queued update without a draw; the next rendered frame overwrites it with current state. This is an implementation ordering choice, not an omitted upload or an immediate execution assumption.

When a resize arrives, only the physical surface extent and logical projection values need updating. When the window is minimized, events and timing continue while drawing is suspended. When an unrecoverable GPU error occurs, the diagnostic flag ends the loop and cleanup releases the known owners. These are branches of the same frame lifecycle, not separate miniature renderers.

18.6Answers you can now derive#

QuestionAnswer grounded in this program
Why an adapter before a device?Choose a surface-compatible capability provider before creating the resource-owning connection
Why does the surface have a format?Its images need a defined representation and color interpretation that the pipeline’s output matches
Why locations and vertex layouts?The GPU reads untyped bytes and must route decoded attributes into a particular shader interface
Why encode instead of immediate drawing?The implementation validates and batches coherent work while CPU and GPU proceed asynchronously
Why acquire every frame?The current presentation image is a frame-scoped resource managed by the surface
Why two triangles?TriangleList describes filled triangle coverage; six corner references cover the rectangle
What moves the character?A CPU position update becomes uniform bytes, then different clip positions and rasterized coverage
What survives resizing?Device, queue, pipeline, layouts’ retained dependencies, buffers, and bind group; only presentation extent and uniform view values change

18.7Keep this program small enough to understand#

The final renderer is deliberately not an engine. There is no hidden scene graph, automatic batching system, or resource cache. You can add a feature later by locating the contract it changes: a texture changes shader resources and upload work; a second character changes per-draw data management; rotation changes the transform. The moving geometric character completes the foundation. Next we will add sampled artwork and build the room, preserving the native connection and frame-lifetime rules. It contains enough native WebGPU machinery to make future decisions informed rather than ceremonial.

18.12Challenges#

Optional extensions. The complete game in chapter 23 requires none of these. Work in a separate copy if you want to explore; the next chapter starts from this chapter’s supplied baseline.

  1. A reproducible replay

    Represent a short sequence of direction/time pairs as CPU data and feed it through update in a diagnostic mode. Keep ordinary keyboard input as the default.

    Check your result: Repeated replays end at the same position within floating-point tolerance.

  2. A second controlled character

    Add another game state and a different input mapping. Give each draw independent uniform storage or ranges.

    Check your result: Each character moves and changes appearance independently without moving input logic into the renderer.
