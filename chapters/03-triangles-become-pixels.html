3.1Follow one covered point#

Imagine a rectangle’s four corners written on paper. Those corner records describe the boundary, not every point inside it. Two triangles tell the GPU which interior to cover. Rasterization is the step that determines which image sample locations those triangles cover. The fragment shader then supplies a color contribution at those locations.

The vertex shader answers “where does this corner go?” and the fragment shader answers “what color does this part contribute?” Neither controls the desktop window. The CPU arranges the work and chooses the destination. Keeping these jobs separate explains why adding more detail to a face need not add more corners.

For our 2D case, w = 1 makes the perspective division harmless. A clip position of (0, 0, 0, 1) lands at the center of the viewport; (−1, +1, 0, 1) is its upper-left boundary. You can understand this renderer with multiplication, division, and coordinate pairs. Matrices are not a prerequisite.

3.2We describe boundaries, not a list of pixels#

A pixel is one sample location in the output image’s grid. A vertex is a piece of input data describing a point and, eventually, additional values such as color. A rectangle 48 units wide and 64 units tall can cover thousands of pixels but needs only four corner records. The GPU fills the interior from those boundary descriptions.

Our chosen primitive topology will be a triangle list. Every group of three vertex references describes one triangle. Triangles are especially useful because three non-collinear points define a planar surface with an unambiguous interior. A general polygon could be concave or nonplanar; decomposing it into triangles removes those ambiguities. WebGPU can also draw points and lines, but filled 2D characters fit naturally into triangles.

The diagonal in this diagram is an internal boundary, not a visible line. Two triangles cover the rectangle. Rasterization’s edge-coverage rules assign shared-edge samples consistently; we do not add an outline pass or manually fill the seam. Four corners can be referenced by six indices, which we will implement after understanding ordinary vertex input.

3.3The pipeline is a series of transformations#

The CPU prepares data and records commands. During GPU execution, vertex fetch reads the vertex data according to a layout. The vertex shader runs for vertex invocations and produces a four-component clip position. Primitive assembly groups outputs into triangles. Clipping removes or cuts portions outside the permitted volume. Rasterization determines covered samples and interpolates values across the triangle. The fragment shader computes colors for candidate contributions to the image. Finally, output operations write or blend those colors into a render target.

A fragment is not always identical to one final visible pixel. Rasterization may generate fragments that later fail tests, multiple triangles may contribute to the same pixel, and multisampling can use multiple coverage samples. Our simple renderer uses one sample and no depth test, so thinking “a candidate color contribution near a pixel” is enough. Even here, overlapping draws can write the same pixel more than once.

A shader is a program executed by the GPU as one stage of this pipeline. The vertex shader does not explicitly call the fragment shader. It returns data; the fixed stages between them generate the work for the next shader. Our host application selects shader entry points when creating a render pipeline.

3.4Why a 2D position needs four output numbers#

WebGPU vertex shaders output clip coordinates (x, y, z, w). Visible geometry satisfies −w ≤ x ≤ w, −w ≤ y ≤ w, and 0 ≤ z ≤ w, before division by w. Dividing x, y, and z by w produces normalized device coordinates, abbreviated NDC. In this book we always choose z = 0 and w = 1. The division changes nothing, and the useful x/y interval is simply −1 to +1.

NDC (−1,+1) is the upper-left boundary of the viewport; (+1,−1) is its lower-right boundary. Positive NDC y points upward. Window coordinates normally increase downward from the upper-left. That sign difference will account for the minus sign in our pixel conversion. The boundary at x=+1 is the right edge, not the center of the last pixel. Pixel centers lie inside the image, typically at half-integer framebuffer positions.

A viewport maps the normalized rectangle into a region of the render target. Its default covers the attachment. A scissor rectangle limits which framebuffer region may be written. A smaller scissor crops; it does not scale coordinates. We need neither an explicit viewport nor a scissor for a full-window character, but we will use each as a debugging experiment once a render pass exists.

3.5The CPU is ahead of the GPU#

A draw call made through a render-pass encoder records a command. It does not mean the GPU has finished drawing by the time the function returns. Recording lets the implementation validate coherent state, translate many commands into backend work, and submit a useful batch. The GPU can execute previously submitted work while the CPU prepares the next frame. It would be costly to force a CPU/GPU round trip after every state change or triangle.

This separation explains objects that otherwise look ceremonial. A command encoder owns a mutable recording. Finishing it produces a command buffer, an immutable sequence ready to submit. The queue receives that sequence in an ordered stream. The render pass declares the images being used together as attachments and the intended handling of their contents. Each object expresses an execution or resource boundary that the implementation needs.

3.11Challenges#

Optional extensions. The complete game in chapter 23 requires none of these. Work in a separate copy if you want to explore; the next chapter starts from this chapter’s supplied baseline.

  1. Plan a diamond marker

    Sketch a diamond from a top, right, bottom, and left corner. List two triangle triplets that cover it. Save the sketch for chapter 10, where you can implement it.

    Check your result: The triangles share one edge and cover the diamond without a gap.

  2. Plan a split view

    Draw two viewports in one window and map NDC center and corner points into each. This is a design exercise; chapter 13 introduces the calls needed to implement it.

    Check your result: The same NDC point maps to different framebuffer positions in the two viewports.
