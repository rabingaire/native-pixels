9.1Let Odin supply the corners#

The triangle’s corners currently live inside WGSL. We will move that data into Odin, copy it into a GPU buffer, and tell the pipeline how to read each corner. A different color at each corner will make the data flow visible.

The new problem is a byte-layout problem: Odin stores a record, WebGPU reads its fields, and WGSL receives the values. We will calculate one record’s size and offsets before changing the shader and buffer setup.

9.2Count the bytes in one corner#

An f32 stores a floating-point number in 32 bits, or four bytes. Floating-point numbers represent fractions with limited precision, which lets us place a corner between whole-number coordinates. An array [2]f32 holds x and y in eight bytes. Odin also lets us read those components as .x and .y.

Our new Vertex struct stores two position numbers and four color numbers. RGB gives red, green, and blue; the fourth value, alpha, is 1 for the opaque colors in this chapter. Six f32 values require 24 bytes. size_of(Vertex) asks for the actual size, and offset_of(Vertex, color) asks where the color field starts.

#assert checks a condition while compiling. We use it to stop the build if the struct layout differs from the byte layout we tell WebGPU to read. This agreement between Odin memory and the graphics interface is a small example of an application binary interface, or ABI. Matching names is not enough; the bytes must agree.

9.3Move geometry out of the shader#

The hard-coded array proved the shader pipeline. It becomes awkward as soon as geometry belongs to the application rather than to shader source. A GPU buffer gives us a persistent region of bytes usable by GPU operations. The CPU owns a native handle, while the implementation chooses suitable backing storage. We cannot assume that storage is an ordinary CPU array, even on a machine with unified memory.

Add the Vertex struct and three-element VERTICES constant to renderer.odin. The constant is CPU-side data compiled into the program. The WebGPU buffer created from it is a separate object. Change the WGSL vertex entry point to read attributes rather than vertex_index. This deliberately removes the temporary shader array introduced in chapter 8.

Next record begins 24 bytes laterarrayStride = 24, stepMode = VertexA new record for the next vertex index

The stride is the distance in bytes from the beginning of one vertex record to the beginning of the next. An attribute’s offset is measured from the beginning of its record. The GPU effectively reads buffer_base + vertex_number × stride + attribute_offset, then interprets those bytes according to the format. The shader location identifies the destination parameter; the parameter’s name is not part of this matching process.

Our struct contains arrays of scalar f32 values. Its position begins at byte zero and its color at byte eight, with size 24. Compile-time assertions make that ABI explicit. These assertions check the actual record layout instead of assuming that the compiler arranged it as we expected.

In src/renderer.odin: Inside renderer_init, insert these two declarations immediately before descriptor := wgpu.RenderPipelineDescriptor. Also add bufferCount = 1 and buffers = &vertex_layout to descriptor.vertex, as shown in the complete file. Complete file with surrounding code.

attributeCount and attributes describe the array of two attributes. bufferCount = 1 and buffers = &vertex_layout are added to the pipeline’s vertex stage. Buffer slot zero describes one stream of interleaved position/color records. It is independent of shader locations zero and one. Multiple attributes can come from the same buffer slot, as they do here.

9.5Allocate once, upload once#

In src/renderer.odin: Inside renderer_init, insert this block at the beginning of the body, immediately before source :=. Keep the shader and pipeline setup that follows. Complete file with surrounding code.

.Vertex allows vertex fetch from the buffer. .CopyDst allows writes through the queue. Flags are capabilities of the resource, not the operation we happen to perform first. Leaving out CopyDst is a validation error when uploading, even if the buffer size is correct. Buffer allocation by itself does not copy our constant into GPU storage.

QueueWriteBuffer copies the supplied CPU bytes into implementation-managed upload storage as part of the call, with the GPU-visible write ordered through the queue. The local vertices copy exists to supply an addressable range for that call; it can go out of scope afterward. We do not map the vertex buffer, block for GPU completion, or retain a pointer to the local array. The data size is 72 bytes, a multiple of four, satisfying the write operation’s alignment requirement.

9.6Interpolate values across the triangle#

WGSL can return a struct, just as Odin can. Vertex_Out groups the clip position and a color in one result. The local out value is declared with var because the function assigns its fields before returning it. The location numbers connect the vertex result to the fragment input.

In shaders/character.wgsl: Replace the entire file with this listing. Complete file with surrounding code.

The vertex shader returns a struct with a built-in clip position and a user color at location zero. The fragment shader receives the interpolated color at that location. Do not confuse its location zero with the vertex input color at location one: these are different stage interfaces. Locations connect outputs to inputs at a particular stage boundary, not a single global namespace.

Interpolation computes values between the ones supplied at the corners. Halfway along an edge between red and blue corners, the interpolated color is an equal mixture. Interior points combine contributions from all three corners. WGSL normally accounts for perspective during interpolation; here every w is one, so those contributions vary linearly across the triangle. The smooth colors are calculated during drawing, not stored as extra vertices.
