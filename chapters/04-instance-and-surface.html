4.1A handle, a descriptor, and an owner#

A handle is an opaque reference returned by an API. You keep it to identify an object in later calls; you do not inspect or free the object’s internal memory yourself. A descriptor is ordinary CPU data containing the options for a call. An owner is our application’s chosen place to store a handle and arrange its release. These are three roles, not three interchangeable words for GPU memory.

In Odin, ^GPU is a pointer to a GPU struct, &gpu takes its address, and nil means no pointer or handle. Passing a pointer lets a helper fill the original owner rather than a temporary copy. A native window pointer must be the platform handle the descriptor requests; having the same pointer-sized representation does not make unrelated handles interchangeable.

The instance is the starting context for WebGPU. The surface connects that context to a presentation destination backed by our already-created window. We create the surface before selecting an adapter so selection can ask for a GPU that can actually present there. Configuration comes later, after we have a device to render the images.

4.2A connection before a device#

A WebGPU instance is the application’s entry into the native implementation. It can discover adapters and create surfaces. It is not a physical GPU and owns no character vertices. It is mostly a CPU-side API object that holds implementation and backend context. We create one for this application and keep it until every dependent object has been released.

A surface describes a destination that the operating system can present. It wraps a native window-related object. A surface is not a permanent texture containing the screen, and creating one does not select a resolution or allocate our vertex buffer. Later, configuration will connect this surface to a device and choose the kind of presentable images we can acquire.

4.3Give the connection an explicit owner#

Add src/gpu.odin. Its GPU struct groups the long-lived connection handles. The name is a convenient application owner, not a claim that every field lives in physical GPU memory. Add gpu_init and gpu_destroy as shown. Initialization may stop partway; destruction tolerates that partial state.

CreateInstance(nil) asks for the implementation’s default instance configuration. In this binding the small wrapper checks the linked wgpu-native version before calling the native entry point. We do not request special backend extensions. A descriptor would be useful for nondefault instance requirements, but a pointer to an empty descriptor is not more educational than a deliberate default.

Inside main(), add a local gpu: GPU after window creation. Register defer gpu_destroy(&gpu) before calling initialization so partial failure is cleaned up. Then return if gpu_init(&gpu, window) fails. The window’s earlier defer will run after the GPU cleanup. The complete changed main appears in this chapter’s snapshot.

4.4The bridge is ordinary Odin#

Add src/platform.odin. This is the only platform conditional in surface creation. Read your platform’s branch now; the complete cross-platform file is below in the source snapshot. We are not importing vendor:wgpu/sdl3glue: owning this small bridge also makes the extra macOS view’s destruction visible.

On macOS, SDL creates a Metal-capable view and returns its underlying CAMetalLayer. That layer is the object a Metal-backed WebGPU surface can present into. It is obtained through SDL’s C ABI, so we need no Objective-C or C helper. We retain the MetalView handle and destroy it only after releasing the WebGPU surface. An NSWindow pointer by itself is not the Metal layer.

SDL3 exposes these values through window properties. This replaces recipes based on SDL2’s SysWM information structs. On Linux we inspect SDL’s actual video driver before choosing a descriptor: X11 and Wayland handles are not interchangeable. A headless or dummy SDL driver has no supported desktop surface here and is rejected with a diagnostic.

4.5Why descriptors have a chain#

SurfaceDescriptor carries portable fields such as a label, plus a pointer named nextInChain. Its extension begins with a ChainedStruct containing an sType discriminator. The implementation follows that pointer and interprets the remainder according to the discriminator. The pointer does not point at an arbitrary platform object; it points at a specifically tagged descriptor that contains the platform object.

The source descriptor and top-level descriptor are local CPU structs. They need to remain valid while InstanceCreateSurface reads them. The resulting surface handle outlives them. The native window and layer, however, must remain usable throughout the surface’s lifetime. Mixing these two lifetimes—short descriptor storage and long native object storage—is a common interop mistake.

Native versus JavaScript

Browser WebGPU receives a canvas context from the browser. It does not expose Win32, X11, Wayland, or Metal-layer descriptor chains. The native surface fills the equivalent presentation role, with explicit host ownership.

4.10Challenges#

Optional extensions. The complete game in chapter 23 requires none of these. Work in a separate copy if you want to explore; the next chapter starts from this chapter’s supplied baseline.

  1. Explain the platform bridge in logs

    Add one startup diagnostic naming the selected platform branch and whether its required native handles were obtained. Report the stage on failure without dumping raw pointers.

    Check your result: A failed handle lookup identifies the missing platform property and still follows cleanup.

  2. Make ownership visible

    Add temporary creation and release messages for the instance, surface, and Metal view where applicable. Keep them behind one debug flag.

    Check your result: Normal close and a forced early return show that each successfully created object is released once, in dependency order.
