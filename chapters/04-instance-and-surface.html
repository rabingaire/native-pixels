4.1Connect the window to WebGPU#

SDL already owns a responsive window. To draw into that window, WebGPU needs a connection to its native drawing destination. That connection is called a surface. An instance is the WebGPU object used to create it.

We will add src/platform.odin for the operating-system-specific connection and src/gpu.odin to keep its handles together. First we will learn structs and ownership, then create the connection, and finally add cleanup. The window will still have no application-drawn pixels.

4.2Group related values in a struct#

We now need to keep more than one graphics handle. A struct groups related values under one name. Each named value inside it is a field. The complete example below shows how a helper changes a field through a pointer. Read it on its own; do not paste it into your game or replace your existing main. The game changes follow after this explanation.

The Counter declaration and increment procedure are outside main, after the package line. Between main’s opening and closing braces, the first line creates counter; the very next line calls increment. This example ends there and prints nothing.

Counter{value = 2} creates a struct value with a named field. ^Counter is the type “pointer to Counter.” The call passes &counter, so the procedure changes the original counter. Odin lets us access fields through the pointer using counter.value. counter^ means the entire value at the address.

A procedure can return a result: proc(...) -> bool returns true or false. Our initialization helpers return false when they cannot finish. An empty struct value {} resets all fields to their zero values. Pointer and native-handle fields then contain nil, meaning no object. This lets cleanup distinguish objects that were created from objects that are still absent.

Some platform fields use u32 or u64: unsigned whole numbers stored in 32 or 64 bits. A conversion such as u64(window_id) makes the expected type explicit. Use the type required by the API field; the same numeric value can occupy different amounts of memory in different types.

A handle is a value returned by a library that identifies one of its objects. We pass the handle back to that library instead of accessing the object’s internal memory. A descriptor is a struct containing options for creating an object. An owner is the part of our application responsible for keeping and releasing a handle. The descriptor, the handle, and the owner have different jobs.

4.3A connection before a device#

A WebGPU instance is our starting object for the native graphics library. It lets us create a surface for the existing window. Create the instance once and keep it until cleanup has released the surface. The name “instance” here means this library context, not an extra copy of a character.

A surface identifies the window destination that WebGPU will present images to. Creating the surface connects the graphics library to that destination. It does not draw a frame or choose the image dimensions yet. We will make those choices after creating a device.

4.5Why descriptors have a chain#

The ordinary SurfaceDescriptor contains a label and a nextInChain pointer. Window systems need different extra information, so this pointer selects a second descriptor holding the platform-specific fields. Its sType field identifies their type. For macOS we use SurfaceSourceMetalLayer; the fields then include a pointer to the layer. Both descriptors are ordinary structs on the CPU.

InstanceCreateSurface reads the two descriptors during the call. They may be local variables because we need their values only during that call. The returned surface has a longer lifetime. The native window and layer must also remain alive for as long as the surface uses them. Temporary settings and the objects described by those settings have different lifetimes.

On macOS, SDL creates a Metal-capable view and returns its underlying CAMetalLayer. That layer is the object a Metal-backed WebGPU surface can present into. It is obtained through SDL’s C ABI, so we need no Objective-C or C helper. We retain the MetalView handle and destroy it only after releasing the WebGPU surface. An NSWindow pointer by itself is not the Metal layer.

SDL3 exposes these values through window properties. This replaces recipes based on SDL2’s SysWM information structs. On Linux we inspect SDL’s actual video driver before choosing a descriptor: X11 and Wayland handles are not interchangeable. A headless or dummy SDL driver has no supported desktop surface here and is rejected with a diagnostic.

4.7Release the surface before its window#

The surface refers to the native window or layer. Release the surface first, then any Metal view, and finally the SDL window. Reset the owner to an empty struct after releasing its handles.

Native versus JavaScript

Browser WebGPU receives a canvas context from the browser. It does not expose Win32, X11, Wayland, or Metal-layer descriptor chains. The native surface fills the equivalent presentation role, with explicit host ownership.
