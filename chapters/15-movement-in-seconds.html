15.1Use units to check the movement equation#

Speed is distance per second. Multiplying 240 units/second by 1/60 second gives 4 units; the seconds cancel. At 144 updates per second, each step is about 1.667 units. More smaller steps and fewer larger steps cover approximately the same distance when the elapsed time is the same and the stall cap is not reached.

A direction of (1,1) has length √2, so it must be shortened to a unit vector before applying speed. Normalization preserves direction while changing length to one. Skip division for the zero vector. Keep simulation positions as floating-point values so small fractions accumulate instead of disappearing.

The 0.05-second cap is a deliberate responsiveness policy: after a long interruption we simulate at most a small step, discarding the rest. It prevents a surprising jump, but it does not make the simulation replay all real elapsed time. Timing the loop, timing GPU execution, and waiting for GPU completion are separate operations.

15.2A distance for this iteration#

If we add four units every frame, the character travels 240 units per second at 60 frames per second and 576 at 144. That ties gameplay to presentation frequency. Instead define a speed in logical units per second and multiply by elapsed seconds: distance = speed × dt. The GPU does not need to understand time; it only receives the resulting position.

Add speed: f32 to Game and set it to 240 in main. Record previous_ticks := sdl.GetTicksNS() immediately before the loop. After draining events and checking running, measure the new timestamp, compute elapsed seconds, and advance the previous timestamp. Subtract in integer nanoseconds before converting; converting two large uptime values to f32 before subtraction would lose useful precision.

The timestamp update occurs before minimized/zero-size early continues. Time does not accumulate unnoticed while the window is suspended. The 0.05-second maximum prevents a debugger pause or long window drag from producing a huge jump. This is a deliberate policy: very long stalls discard elapsed simulation time, so the program slows relative to wall time during those stalls. “Frame-rate independent” means ordinary uncapped steps integrate a speed in seconds; it does not promise to replay every missed second under the cap.

15.3Normalize intent before applying speed#

Replace the temporary tint-only game_update in game.odin with the movement procedure below. Add core:math for the square root. In main, pass f32(dt) and view_size to this procedure. All other input and render ordering stays the same.

A direction of (1,0) has length one. A direction of (1,1) has length √2, which would make diagonal movement faster. Divide a nonzero direction by its length before multiplying by speed and time. Check for nonzero length first: normalizing (0,0) would divide by zero and contaminate position with invalid values that can later make all geometry disappear.

At 60 Hz, dt is about 1/60 second and a cardinal step is 4 units. At 144 Hz, it is about 1.667 units. After one second of steady input, both advance approximately 240 units. The use of floating-point positions allows fractional steps; converting position to an integer every update would discard small movements and reintroduce frame-rate-dependent errors.

15.4Keep the character reachable#

After applying motion, clamp the top-left x to [0, view_width − character_width] and y similarly. This keeps the whole rectangle inside the logical window when the window is large enough. If the window is smaller than the character, the maximum becomes negative; taking max with zero makes the permitted position zero instead. The character then extends outside the tiny window and is normally clipped.

This clamp is a game rule, not a GPU requirement. Removing it would simply let the character leave the visible area. It also repositions the character if a resize makes its old position invalid. An application with a larger persistent world would likely keep world position and move a camera instead; our intentionally window-sized project uses the simplest explicit behavior.

The renderer receives the updated position and writes it to the uniform buffer. Local vertices stay the unit square. The vertex shader computes four new clip positions, and rasterization covers a different set of samples. No texture is slid across the desktop and no previously drawn pixels are moved. Every frame clears and draws the character again at its current position.

15.5Timing and GPU synchronization are different problems#

Delta time measures the CPU application’s iteration interval using SDL’s clock. It is not the GPU execution duration, the number of presented refreshes, or a fence. Submission and presentation may apply backpressure, which becomes part of the elapsed interval measured on the next iteration. We do not divide by an assumed monitor refresh rate or use a hard-coded 1/60 in the real application.

A fixed simulation step can be useful for physics and deterministic update systems, but none is required for integrating this simple movement vector. Adding an accumulator here would hide the relationship between elapsed time, position, and uploaded data behind a second timing system. Our variable-step update is enough for this focused project, with its explicit stall cap.

A bounded smoke check is different

The repository’s verification harness supplies a fixed test direction and time step to exercise predictable motion while rendering real GPU frames. That harness is not the final application. Normal input and timing remain SDL-driven in project/src.

15.8Experiments#

These short, optional checks help you test the explanation. Predict the result first, then run the program. Restore the chapter’s baseline before continuing; later chapters assume the supplied checkpoint.

  1. Change speed to 120. It should take about twice as long to cross a fixed distance during ordinary running.
  2. Compare motion with and without a short artificial delay at the end of the loop. Below the stall cap, fewer frames should produce larger steps and a similar distance per second.
  3. Temporarily remove normalization and compare cardinal and diagonal travel distances. Restore it before continuing.

15.10Challenges#

Optional extensions. The complete game in chapter 23 requires none of these. Work in a separate copy if you want to explore; the next chapter starts from this chapter’s supplied baseline.

  1. Sprint without diagonal advantage

    Add a held sprint input that changes speed before calculating displacement. Keep normalization and the seconds-based step.

    Check your result: Sprint multiplies cardinal and diagonal travel by the same factor.

  2. Acceleration and braking

    Store velocity in game state and move it toward a target velocity at a rate measured in units/second². Integrate position using dt.

    Check your result: The character starts and stops gradually, and comparable uncapped elapsed times give similar travel at different update rates.
