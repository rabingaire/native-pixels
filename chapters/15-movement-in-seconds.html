15.1Move by distance per second#

Holding a direction key changes tint, so the path from SDL input to the rendered character works. We will now use the same direction to change position.

Moving a fixed amount per loop would make faster computers move farther. We will measure elapsed seconds, multiply by speed, and keep diagonal movement at the same speed as horizontal movement. Then we will stop the character at the view’s edges.

15.2A distance for this iteration#

If we add four units every frame, the character travels 240 units per second at 60 frames per second and 576 at 144. That ties gameplay to presentation frequency. Instead define a speed in logical units per second and multiply by elapsed seconds: distance = speed × dt. The GPU does not need to understand time; it only receives the resulting position.

Add speed: f32 to Game and set it to 240 in main. Record previous_ticks := sdl.GetTicksNS() immediately before the loop. After draining events and checking running, measure the new timestamp, compute elapsed seconds, and advance the previous timestamp. A nanosecond is one billionth of a second. The timestamps are integers; f64 converts their difference to a 64-bit floating-point value. Divide by one billion to get seconds, and min chooses the smaller of that result and 0.05. Subtract in integer nanoseconds before converting; converting two large uptime values to f32 before subtraction would lose useful precision.

The timestamp update occurs before minimized/zero-size early continues. Time does not accumulate unnoticed while the window is suspended. The 0.05-second maximum prevents a debugger pause or long window drag from producing a huge jump. This is a deliberate policy: very long stalls discard elapsed simulation time, so the program slows relative to wall time during those stalls. “Frame-rate independent” means ordinary uncapped steps integrate a speed in seconds; it does not promise to replay every missed second under the cap.

15.3Normalize intent before applying speed#

Replace the temporary tint-only game_update in game.odin with the movement procedure below. Add core:math for the square root. In main, pass f32(dt) and view_size to this procedure. All other input and render ordering stays the same.

In src/game.odin: Replace the entire game_update procedure, including its body, with the version below. Keep the rest of the file. Complete file with surrounding code.

A direction of (1,0) has length one. A direction of (1,1) has length √2, which would make diagonal movement faster. Divide a nonzero direction by its length before multiplying by speed and time. Check for nonzero length first: normalizing (0,0) would divide by zero and contaminate position with invalid values that can later make all geometry disappear.

At 60 Hz, dt is about 1/60 second and a cardinal step is 4 units. At 144 Hz, it is about 1.667 units. After one second of steady input, both advance approximately 240 units. The use of floating-point positions allows fractional steps; converting position to an integer every update would discard small movements and reintroduce frame-rate-dependent errors.

15.4Keep the character reachable#

After applying motion, clamp the top-left x to [0, view_width − character_width] and y similarly. This keeps the whole rectangle inside the logical window when the window is large enough. If the window is smaller than the character, the maximum becomes negative; taking max with zero makes the permitted position zero instead. The character then extends outside the tiny window and is normally clipped.

This clamp is a game rule, not a GPU requirement. Removing it would let the character leave the visible area. It also repositions the character if a resize makes its old position invalid. An application with a larger persistent world would likely keep world position and move a camera instead; our intentionally window-sized project uses the simplest explicit behavior.

The renderer receives the updated position and writes it to the uniform buffer. Local vertices stay the unit square. The vertex shader computes four new clip positions, and rasterization covers a different set of samples. No texture is slid across the desktop and no previously drawn pixels are moved. Every frame clears and draws the character again at its current position.

15.5Timing and GPU synchronization are different problems#

Delta time measures the CPU application’s iteration interval using SDL’s clock. It is not the GPU execution duration, the number of presented refreshes, or a fence. Submission and presentation may apply backpressure, which becomes part of the elapsed interval measured on the next iteration. We do not divide by an assumed monitor refresh rate or use a hard-coded 1/60 in the real application.

For this application, each update uses the measured dt. The 0.05-second cap keeps a pause from becoming a large movement jump. It does discard time after a long stall, so the simulation will not cover the full real-world elapsed interval in that case. This is a responsiveness choice, not a promise of identical results under every timing condition.

  2. Compare motion with and without a short artificial delay at the end of the loop. Below the stall cap, fewer frames should produce larger steps and a similar distance per second.
