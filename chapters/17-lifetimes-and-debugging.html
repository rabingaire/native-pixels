17.1Reason about failure one acquisition at a time#

Consider initialization that creates a vertex buffer but fails before creating an index buffer. Cleanup must release the vertex buffer and skip the absent index buffer. A zero-initialized owner plus conditional releases makes this partial state representable. Register cleanup early enough that a helper returning false still unwinds everything it already created.

Now consider a frame that acquires a texture but fails to create a view. The texture still needs release. Defers belong immediately after successful acquisitions, before later operations can return. This local reasoning is more reliable than one long success-only cleanup list at the bottom of a procedure.

A recoverable skip means this attempt cannot produce an image but a later attempt may succeed. Device loss means the resources owned by that device cannot simply be assumed usable. The book deliberately exits on that failure. Retrying surface configuration is not an implementation of complete device recreation.

17.2Two kinds of lifetime must agree#

The application owns native references. The implementation owns backend objects and retains what submitted work needs. These lifetimes overlap, but are not identical. A local pointer variable going out of scope does not automatically release a native object. Calling Release decrements an application reference; it is not a synchronous command that frees all backend memory immediately.

Destroy has a different meaning for resources such as buffers: it explicitly invalidates the resource for future use and schedules its storage for reclamation when safe. It is not a substitute for releasing the native handle. This program generally uses Release when its owner is finished. It never calls TextureDestroy on a borrowed-current presentation image in place of presenting and releasing it.

17.3Read the cleanup we already wrote#

Main registered GPU cleanup before renderer cleanup, so the renderer’s defer runs first. Releasing renderer references does not invalidate work already submitted by the preceding frame; the backend retains its in-flight dependencies. GPU cleanup then drains queued work, unconfigures the surface, and releases queue/device/adapter references. Finally the platform owner releases the surface and its Metal view, and the earlier main defers destroy the window and quit SDL.

The cleanup procedures check each handle and reset their owner struct afterward. That accommodates an initialization failure halfway through renderer setup. Native Release functions generally do not accept nil as a harmless no-op, so each check matters. The process-lifetime diagnostic flag remains available even while teardown can trigger native callbacks. A normal device-destroyed loss reason is ignored; actual failures are reported.

We wait at shutdown for simplicity, not once per frame. A per-frame DevicePoll with wait=true would turn the CPU/GPU pipeline into a serial handshake. It is valid to wait when the CPU genuinely needs a completed GPU result, such as a readback operation. Our moving rectangle never reads GPU memory back, so normal rendering needs queue ordering, not a CPU completion fence.

Know the limits of error recovery

This edition reports and exits on device or surface loss. It does not promise transparent GPU recovery. Native wgpu-native can also treat certain invalid-handle/API misuse paths as fatal before ordinary callbacks can recover. Guards, correct descriptors, and pinned API verification remain necessary.

17.5Debug from the last fact you can prove#

For a black window, first choose a conspicuous clear color. If that appears, acquisition, attachment setup, and submission/presentation have worked for that frame. Next use the constant-color triangle checkpoint. If that works but the final character does not, the first differences to inspect are vertex layout, indices, uniform layout, and transform values. An error callback with a labeled resource often points directly to the violated contract; read its first message before speculating about the driver.

For a character that does not move, inspect the chain in order: direction after SDL polling, dt in seconds, game.position after update, uniform.position before QueueWriteBuffer, and the shader’s usage of that field. If CPU position changes but uniform.position remains a literal, the GPU is correctly rendering stale data. Rebuilding pipelines or changing presentation modes cannot repair that disconnected value.

For distorted geometry, calculate the byte address of vertex one’s position from stride and offset. Compare it with the actual struct assertions. Check whether the index format matches u16. Then calculate the character’s four NDC corners from position, size, and view extent. A known correct byte layout plus known correct corners makes a shader/pipeline problem much more specific than “graphics are broken.”

Use labels already attached to resources: “character uniforms,” “character pipeline,” and “window color pass” turn backend diagnostics into references to our application. Error scopes can isolate expected validation experiments, and GPU capture tools can inspect submitted work, but neither is required to reason through this small pipeline. Temporarily add targeted logs rather than printing every field every frame and burying the first useful error.

17.6An orderly frame is the cheapest lifetime check#

Count the per-frame creates and acquisitions, then their matching releases. A successful render creates a view, encoder, pass, and command buffer and obtains a texture reference. Each has exactly one cleanup on every subsequent exit path. The persistent objects have no per-frame creation sites. Memory that grows without bound after thousands of frames is therefore a reason to inspect the native reference paths before inventing an allocator system.

No implementation changes are introduced in this chapter. The checkpoint is identical to chapter 16. Reviewing the existing lifetimes is a finished capability: you can now explain why returning from a frame is safe while the GPU might still be busy, and why descriptor locals can disappear even though their created objects survive.

17.9Experiments#

These short, optional checks help you test the explanation. Predict the result first, then run the program. Restore the chapter’s baseline before continuing; later chapters assume the supplied checkpoint.

  1. Temporarily break the uniform minimum size and observe which labeled validation diagnostic appears. Restore the valid layout before continuing.
  2. Walk every return path in renderer_frame and mark the resources alive at that point. Check that their defers cover them.
  3. Minimize and restore repeatedly. The application should remain responsive and avoid configuring zero-sized images.

17.11Challenges#

Optional extensions. The complete game in chapter 23 requires none of these. Work in a separate copy if you want to explore; the next chapter starts from this chapter’s supplied baseline.

  1. A controlled failure switch

    Add development-only return points after selected successful initialization steps. Use ordinary cleanup rather than passing invalid handles to the native API.

    Check your result: Every forced stop reports the stage and releases only the resources already acquired.

  2. A small diagnostic summary

    Track initialization stage, last acquisition result, and successful frame count. Print the summary when the program exits after a graphics error.

    Check your result: A failure report tells you the last successful boundary without thousands of per-frame log lines.
