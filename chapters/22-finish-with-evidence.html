22.1Choose evidence that can answer the question#

A compiler can prove that host types and imports are accepted; it cannot prove that a driver accepts a WGSL pipeline. A collision test can prove a contact position; it cannot show whether the artwork looks the right size. A screenshot can show visual alignment; it cannot prove every movement path. These checks complement one another.

F1 draws the actual authored solids and the current feet box over the room. Orange outlines mark obstacles, and green marks the feet. At the chair, the box should touch an edge without entering it. The body may overlap painted furniture because it is drawn above the floor; the overlay makes that intentional rule visible.

This checkpoint adds diagnostics to the still-image character. Chapter 23 supplies the final animated player and its adjusted visual scale. The verification screenshots are captures of that final application, so the pose and apparent size can differ from this checkpoint even though the colliders are the same.

22.2Make invisible rules visible#

A professional workflow does not depend on remembering eleven collision rectangles while looking at a picture. We add an F1 overlay so the game can show its own geometry through the renderer’s existing Rect API. This is a diagnostic feature with immediate value, not the start of a general UI system. Orange outlines show solids, and a green outline shows the true floating-point feet box.

In main’s event switch, add the KEY_DOWN case shown below. This is edge-triggered input: toggle once for the press event, ignoring OS key-repeat events. Movement still uses held keyboard state after polling. Those are different input semantics, and both are translated into game.Input before Update.

Add toggle_collision: bool to Input and show_collision: bool to game.State. Update flips the retained state when the input edge is present. Main creates a fresh zeroed Input each loop, so the edge does not remain asserted on following frames. The scene overlay belongs in game.Draw, after the room and character, ensuring its lines remain visible.

An outline is four thin filled rectangles. Rect uses a one-pixel white texture created by renderer.Init; multiplication by tint supplies each line’s color. All overlay rectangles share that texture and are consecutive, so they form one texture run after the room and player runs. Eleven solid outlines plus one feet outline need 48 rectangles; with the two scene sprites, the total is 50, comfortably below 256. Their corners overlap slightly under alpha blending; this is diagnostic geometry, not an exact single-coverage stroked-path renderer.

The feet outline uses the unsnapped simulation position while the player sprite uses rounded display coordinates. A sub-unit discrepancy is intentional and helps reveal the distinction between collision truth and visual snapping. If a table looks too large or a plant can be approached too closely, adjust the authored game box with this view, then update the corresponding regression test where appropriate.

22.3From main to a furnished window#

  • Startup: main initializes SDL video, creates and shows the native window, and retains it until after renderer shutdown. No SDL Renderer is created.
  • Native connection: renderer.Init invokes our unchanged platform and GPU code: instance → surface → compatible adapter → logical device → queue → capabilities and surface configuration. A size-only change later updates the configuration, not the asset set.
  • Rendering interface: Init creates vertex/index/view buffers, two bind group layouts, a nearest sampler, shader module and render pipeline, the view bind group, and an internal white texture. The shader module’s temporary application reference is released after pipeline creation.
  • Game assets: game.Init sets the spawn and speed, embeds and decodes the room/player PNGs through Load_PNG, and stores the two returned texture IDs. Each texture upload creates persistent sampled storage, view, and bind group.
  • Simulation: main pumps SDL events, constructs Input, computes capped dt, and calls game.Update. Update normalizes direction and clips the requested displacement against the authored solids.
  • Scene description: Begin_Frame resets reusable CPU recording storage. game.Draw appends the background, the snapped player quad, and optionally diagnostic rectangles.
  • Actual frame: End_Frame processes native callbacks, refreshes physical surface size if needed, acquires the current image, creates its view, uploads current vertices/view data, records an ordered render pass, finishes, submits, and presents.
  • Cleanup: per-frame handles are released via defer. Closing the window or encountering an unrecoverable error unwinds persistent renderer resources before SDL destroys the window and quits.

22.4One D press, traced precisely#

SDL pumps the keyboard event and updates its held-key array. If this window has input focus, main translates D into movement.x = 1. At speed 72 world units/second and dt = 1/60, the requested displacement is 1.2 world units to the right. Update asks Move to clip that X segment, then its zero Y segment. In open floor space the entire 1.2 units is accepted; against a chair only the remaining gap is accepted, possibly zero.

Draw rounds a copy of that resolved foot position and subtracts the sprite’s visual anchor. Sprite expands its four world-space corners and their UVs into CPU vertices. End_Frame writes those bytes into the existing GPU vertex buffer; it does not upload the player PNG again. Queue order makes this frame’s writes visible to the following render commands. The vertex shader maps the new corners into clip space; the viewport maps NDC into the centered physical image region.

Rasterization determines covered samples and interpolates UV and tint. The fragment shader samples the persistent player texture, yielding linear RGB and straight alpha. The pipeline blends it over the previously drawn room in the sRGB surface attachment. Submit hands the recorded work to the GPU queue, Present hands the surface image back to the presentation system, and the display eventually shows the new frame. Neither call proves the monitor has already scanned out the image.

If collision returns zero movement, the same vertices are sent again and the character stays against the chair. If acquisition returns Occluded or Timeout, no visible frame is produced; the simulation and window lifecycle remain CPU responsibilities. “I pressed D but nothing moved” can now be localized: input focus/state, dt, collision result, recorded vertices, queue upload, shader transform, or actual surface presentation.

node tools/verify.mjs; browser checksSource listings, relative links, offline page layoutNative graphics correctness.

The native harness lives outside canonical source. It moves right, approaches the chair, moves left, then approaches the north wall, requiring 450 successful presentations rather than merely 450 loop iterations. It requests two window sizes and injects an SDL F1 event. The chair contact should leave feet.y = 175; the final north-wall contact should leave y = 51. See the recorded verification results for what actually passed on this machine, rather than treating the existence of a test as a passing result.

A manual acceptance pass remains valuable: hold each direction and diagonal; release keys; switch focus away and back; approach both sides of the bed and table; slide past the chair; toggle F1; resize to a narrow window; minimize and restore; close normally. Test on each shipping platform with its actual backend and high-DPI behavior. The provided Windows and Linux branches are not claimed as runtime-verified by the macOS run.

22.6Small production habits to keep#

  • Commit image assets and their prompts/metadata with the source. Pin compiler, bindings, and native library as one reproducible toolchain.
  • Keep a playable checkpoint. Add one behavior and one focused test before expanding the renderer API.
  • Name coordinate units and sprite anchors. Do not let window pixels silently become collision coordinates.
  • Make capacity limits and ownership visible. A small explicit limit is better understood than accidental unbounded work.
  • Distinguish diagnostics from recovery. Device/surface loss exits this program; automatic recreation is not implemented.
  • Use evidence from the failing layer. A unit test cannot certify a native frame, and a screenshot cannot certify a swept collision guarantee.

This checkpoint completes the room’s collision and diagnostics. Chapter 23 adds the final directional animation while retaining the same renderer boundary and collision rules. The renderer is a service the game can use, not the owner of the game. You can now change the room’s content and movement rules without re-learning WebGPU initialization, and change how sprites become GPU work without moving collision into a shader. That is a useful professional foundation because the boundaries are understandable and testable.

22.9Experiments#

These short, optional checks help you test the explanation. Predict the result first, then run the program. Restore the chapter’s baseline before continuing; later chapters assume the supplied checkpoint.

  1. Adjust one furniture collider while watching F1, then encode the desired contact position in a test.
  2. Add a non-solid decoration with Sprite or Rect without changing Update. Explain why it has no collision until explicitly authored.
  3. Trace the same D press while pressed against the chair: identify exactly which values stop changing and which frame operations still occur.

22.11Challenges#

Optional extensions. The complete game in chapter 23 requires none of these. Work in a separate copy if you want to explore; the next chapter starts from this chapter’s supplied baseline.

  1. A movement diagnostic

    Draw a short line or thin rectangle showing requested movement and another showing resolved movement. Keep this behind the diagnostic toggle.

    Check your result: A wall contact shows a nonzero request but zero or shortened resolved displacement.

  2. An automated acceptance route

    Extend the deterministic test route to approach another furniture edge and assert the expected foot coordinate. Count successful presentations separately from attempts.

    Check your result: The route fails on an incorrect collider and ends normally on the intended geometry.
