Every step, in order.

23 chapters. One native program. Every stage has a complete, runnable checkpoint.

I · Establish the ground#

  1. 01A small program, a precise toolchainOne native window. One character. Enough graphics machinery to understand every pixel we ask for.↗
  2. 02A window belongs to SDLBefore an image can be presented, the operating system needs a window that stays responsive.↗
  3. 03How triangles become pixelsA draw describes geometry. The GPU determines which parts of an image that geometry covers.↗

II · Put pixels on the window#

  1. 04Instance and surfaceJoin a portable graphics API to an actual desktop window without hiding the platform bridge.↗
  2. 05Adapter, device, and queueSelect a compatible implementation, open a logical connection, and obtain its ordered stream of work.↗
  3. 06Negotiate the imagesThe window supplies a destination. Capabilities tell us which images the device can present there.↗
  4. 07One clear frameBefore drawing geometry, make the entire presentation path prove itself with one background color.↗
  5. 08The first triangleA shader describes how to process data. A pipeline fixes the contract under which those shaders can run.↗

III · Build a small 2D renderer#

  1. 09Vertex bytes become shader inputsA buffer is bytes. Its layout is the agreement that turns those bytes into positions and colors.↗
  2. 10Four corners, six indicesThe character starts as a rectangle. Reuse its corners instead of duplicating them.↗
  3. 11Coordinates measured in pixelsReplace aspect-dependent normalized geometry with a position and a size you can reason about.↗
  4. 12Let the vertex shader place the characterKeep geometry in place. Send the changing transform through a small, explicitly laid-out uniform buffer.↗
  5. 13Resize without stretchingA desktop window has a logical size and a drawable pixel size. Give each number the right job.↗

IV · Move one character#

  1. 14Give the program game stateThe renderer knows how to draw a position. The game decides which position and color to draw.↗
  2. 15Movement measured in secondsSpeed is a distance per unit time. A frame is not a unit of time.↗
  3. 16Color, alpha, and the final characterGive the rectangle a face, then make transparency an explicit pipeline decision.↗
  4. 17Lifetimes, failures, and debuggingA useful renderer has a reason for every object that survives a frame—and every object that does not.↗
  5. 18From a key press to a presented imageRead the finished application as one system: data has an owner, work has an order, and pixels have a cause.↗

V · A room worth walking through#

  1. 19Pixels from a pictureUpload a room and a transparent character. Replace shader-drawn facial features with sampled color, without changing what a triangle does.↗
  2. 20A renderer the game can useA professional boundary is a small, explicit contract—not a large collection of abstractions.↗
  3. 21Solid furniture, simple collisionA picture can suggest a solid table. Only game rules make it solid.↗
  4. 22Finish with evidenceAdd a collision overlay, audit failure paths, and follow one input all the way through the finished room renderer.↗
  5. 23A character that walksA sprite sheet adds poses, not a new rendering system. Keep direction and time in the game, and select an image region through the renderer API.↗
